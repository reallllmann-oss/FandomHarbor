# Fandom Harbor Studio Visual Direction

Status: Completed for UX-05E Studio Visual Intelligence; awaiting Product Owner acceptance
Phase: UX Design Intelligence
Scope: Studio visual direction only; not final UI, Figma production, implementation, CSS, Tailwind, component design, pixel specification or code

## 1. Studio Purpose

Studio is Fandom Harbor's protected creator workspace.

It exists to help authors create, edit, organize and publish archive works with clarity, confidence and control.

Studio should not behave like a CMS backend, data management panel, SaaS dashboard, enterprise tool suite, Notion clone or admin control center.

Why: UX-01 defines Author emotion as "my works are seriously preserved and my identity boundary is respected"; UX-02 defines Studio as Creation Space rather than backend.
Impact: Authors can focus on safe creation and responsible publication instead of feeling they are managing platform inventory.
Application: UX-06 should review Studio against draft safety, save clarity, publish consequence and reader-facing verification.

## 2. Creator Workspace Identity

The core experience goal is:

**Protected Creator Workspace**

Authors should feel:

- Safe to start a draft.
- Clear about work state.
- Confident that saves are real.
- Aware of publication consequences.
- Able to recover from errors.
- Connected to reader-facing results.
- Respected as creators, not operators of a CMS.

Authors should not feel:

- Inside an admin backend.
- Pressured by analytics.
- Unsure whether content is saved.
- Unsure whether content is public.
- Buried under modules.
- Forced into a productivity app pattern.

Why: Studio has higher interaction density than reader-facing pages, but it must still express Fandom Harbor's archive warmth and trust.
Impact: The workspace can be efficient without becoming cold, generic or growth-driven.
Application: UX-06 should preserve efficient task movement while keeping state language, hierarchy and visual rhythm calm.

## 3. Studio Page Identity

### 3.1 Studio Is

Studio is:

- A private creator workspace.
- A protected author workroom.
- A place for creating and maintaining archive works.
- A state-clear environment for drafts, chapters, metadata and publication.
- A bridge from private creation to public reader-facing work.
- A trust surface for save, validation, publishing and verification.

Why: Authors need a place where creative work and archival responsibility can coexist.
Impact: Studio becomes purpose-built for Fandom Harbor rather than a generic content tool.
Application: Studio should organize around work stewardship, not generic dashboard widgets.

### 3.2 Studio Is Not

Studio is not:

- A CMS backend.
- An admin dashboard.
- A SaaS analytics dashboard.
- A Notion clone.
- A generic productivity workspace.
- A database management panel.
- A marketing or growth console.
- A social creator-performance surface.
- A reader-facing discovery page.

Why: These patterns would replace author control and archive stewardship with administration, productivity theater or growth pressure.
Impact: Authors would lose the feeling that the product understands literary creation and publication risk.
Application: UX-06 should exclude analytics-first layouts, module clutter, admin terminology and database-like management metaphors.

## 4. Creator Workflow Experience

Studio should support a deliberate creation workflow:

```text
Create
-> Edit
-> Organize
-> Publish
-> Verify reader-facing result
```

### 4.1 Create

Create should feel safe and non-public.

Experience needs:

- Clear author capability context.
- Clear draft creation intent.
- Work title and story identity support.
- Metadata responsibility introduced early.
- Visible save state.
- No pressure to publish.

Why: A new work begins as a private archival object, not a public post.
Impact: Authors can start without fear of accidental exposure or loss.
Application: UX-06 should make new-work entry feel deliberate and recoverable without overloading the first step.

### 4.2 Edit

Edit should protect creative focus and save confidence.

Experience needs:

- Body or chapter editing context.
- Current work identity.
- Draft / published distinction.
- Save feedback and error recovery.
- Calm validation when content is incomplete.

Why: Writing and editing involve high emotional cost; unclear save behavior damages trust.
Impact: Authors can focus on story work instead of constantly checking system state.
Application: UX-06 should keep editing state visible and trustworthy without turning editing into a configuration dashboard.

### 4.3 Organize

Organize should help authors maintain works as archive objects.

Experience needs:

- Work list or work grouping by meaningful state.
- Chapter structure.
- Metadata completeness.
- Rating, warning and tag readiness.
- Draft / published / incomplete status clarity.
- Recovery from empty and error states.

Why: Fandom Harbor's archive quality depends on clear metadata and stable structure.
Impact: Authors understand what needs attention before publication and maintenance becomes less risky.
Application: UX-06 should keep organization task-based and state-based, not table-heavy or admin-module-heavy.

### 4.4 Publish

Publish should feel deliberate, reviewable and recoverable.

Experience needs:

- Clear publish intent.
- Reader-facing consequence.
- Save-before-publish confidence.
- Rating, warning and metadata readiness.
- Public identity confirmation where relevant.
- Success state with reader-facing verification path.
- Failure recovery without panic.

Why: Publishing changes visibility and creates reader responsibility.
Impact: Authors can publish with confidence and verify the public result.
Application: UX-06 should treat publish as a meaningful transition, not a generic submit action.

## 5. Visual Direction

Studio visual direction:

**Protected Creator Workspace**

This direction extends Fandom Harbor's quiet editorial brand into a more efficient task surface.

Studio should visually feel:

- Clear.
- Protected.
- Efficient.
- State-aware.
- Calm under pressure.
- Warm enough to belong to a literary product.
- Focused on works rather than metrics.

Studio should not visually feel:

- Corporate.
- Analytical.
- Admin-heavy.
- Over-modular.
- Database-like.
- Growth-oriented.
- Generic productivity software.

Why: Studio must support higher-density work without breaking the Fandom Harbor emotional foundation.
Impact: Authors can act quickly while still trusting the system and understanding consequences.
Application: UX-06 should balance task efficiency with state clarity and literary archive warmth.

## 6. Workspace Philosophy

Studio is a workspace for stewardship.

Direction:

- Organize around works, drafts, chapters, metadata and publication state.
- Keep creator intent visible.
- Keep risky transitions explicit.
- Treat guidance as supportive, not instructional clutter.
- Preserve a path back to reader-facing verification.

Why: Authors are maintaining archive works, not operating a content warehouse.
Impact: Studio feels purposeful and author-centered.
Application: UX-06 should make the workspace structure reflect author responsibility and recovery paths.

## 7. Layout Philosophy

Studio layout should follow a task-and-state rhythm.

Recommended experience rhythm:

```text
Workspace orientation
-> Current work state
-> Create / edit / organize task
-> Save and validation clarity
-> Publish readiness
-> Reader-facing verification
```

Direction:

- Start with where the author is and what needs attention.
- Separate work state from action choices.
- Keep draft and published information visibly distinct.
- Let forms and lists breathe enough to reduce mistakes.
- Use denser layout only where it supports comparison or maintenance.

Why: Studio has operational needs, but unclear density creates anxiety and errors.
Impact: Authors can understand state and act efficiently without backend pressure.
Application: UX-06 should avoid dashboard sprawl, nested cards and admin table dominance.

Non-decision:

- UX-05E does not define sidebar structure, grid, editor layout, breakpoint, sticky behavior or component layout.

## 8. Information Density

Studio can use higher density than reader-facing spaces, but density must be purposeful.

Primary density belongs to:

- Work and draft state.
- Save / publish feedback.
- Chapter structure.
- Metadata completeness.
- Validation and recovery.
- Reader-facing verification path.

Supporting density belongs to:

- Help and policy reminders.
- Secondary author identity context.
- Statistics or response context, if present.
- Non-critical status details.

Why: Author tasks require more information than Reading or Homepage, but equal-weight information becomes CMS noise.
Impact: Authors can scan what matters without feeling buried.
Application: UX-06 should keep analytics, response counts and secondary guidance below work state and publish safety.

## 9. Navigation Philosophy

Studio navigation should follow author intent:

- Create.
- Edit.
- Organize.
- Publish.
- Verify.
- Return to reader-facing work.

Studio navigation should not follow:

- CMS module taxonomy.
- Admin system structure.
- Database table names.
- Enterprise dashboard sections.
- Analytics categories.

Why: Authors think in work states and publishing responsibility, not internal system modules.
Impact: Studio remains understandable and purpose-built.
Application: UX-06 should audit labels and hierarchy for author task meaning, not technical structure.

## 10. Interaction Philosophy

Studio interactions should be deliberate and recoverable.

Interaction direction:

- Save feedback should be clear and honest.
- Publish actions should be explicit and consequence-aware.
- Validation should appear early enough to guide, not only block at the end.
- Destructive or visibility-changing actions should feel serious without panic.
- Primary actions should be few and meaningful.
- Secondary actions should support workflow, not create tool clutter.

Why: Author trust depends on knowing what changed, what is public and how to recover.
Impact: Fewer accidental publishes, less anxiety and better archive quality.
Application: UX-06 should treat save, publish, error and recovery states as primary visual QA criteria.

## 11. Brand Balance

Studio must balance:

```text
Efficiency
+
Fandom Harbor Warmth
```

### Efficiency

Studio needs:

- Clear task paths.
- Fast work scanning.
- State visibility.
- Direct editing and management routes.
- Minimal ambiguity.

Why: Authors return to Studio to do work, not to read brand storytelling.
Impact: The workspace can support repeated use.
Application: UX-06 should keep task surfaces practical and predictable.

### Fandom Harbor Warmth

Studio also needs:

- Calm language.
- Editorial hierarchy.
- Trustworthy state feedback.
- Reader-facing empathy.
- Metadata treated as care for readers, not bureaucratic form-filling.

Why: Studio is still part of a literary archive, and authors should feel their work is being preserved seriously.
Impact: Efficiency does not become cold productivity software.
Application: UX-06 should keep Studio visually connected to the rest of Fandom Harbor through rhythm, wording, semantic states and restrained visual noise.

## 12. Forbidden Experience

Studio must avoid:

- CMS feeling.
- Admin dashboard feeling.
- Enterprise tool feeling.
- Data panel feeling.
- Notion clone feeling.
- SaaS productivity workspace feeling.
- Growth analytics as the primary surface.
- Generic module grids.
- Database table dominance.
- Ambiguous save state.
- Ambiguous publish state.
- Hidden validation until final publish.
- Reader private behavior exposure.
- Public ranking or creator performance framing.
- Social creator economy cues.

Why: These patterns conflict with Studio as protected creator workspace and with Fandom Harbor's private archive identity.
Impact: Avoids author anxiety, category drift and loss of brand trust.
Application: UX-06 should use this list as Studio implementation review guardrails.

## 13. Homepage / Archive / Author / Reading / Studio Relationship

The five visual directions now form a complete product-space model:

```text
Homepage
-> enters the literary harbor

Archive
-> explores the story space

Author
-> recognizes the creator and body of work

Reading
-> enters the story interior

Studio
-> creates and maintains story space
```

### Homepage Relationship

Homepage is the brand threshold.

Why: It establishes Fandom Harbor's private archive meaning and routes authorized authors toward Studio.
Impact: Studio entry should feel like moving into a protected workroom, not leaving the product for a backend.
Application: UX-06 should keep Studio visually connected to the same quiet archive brand.

### Archive Relationship

Archive is the public discovery layer.

Why: Studio's metadata and publication work directly affects Archive quality.
Impact: Authors understand that metadata is a reader-facing discovery responsibility.
Application: UX-06 should connect Studio metadata readiness to how works become discoverable, without creating preview overload.

### Author Relationship

Author Profile is public creator identity.

Why: Studio is where authors prepare the works that later express public identity.
Impact: Authors can understand the private-to-public relationship between workspace and profile.
Application: UX-06 should keep public pen-name context visible when useful without exposing private identity.

### Reading Relationship

Reading is the story interior.

Why: Studio publishes and maintains what readers eventually experience.
Impact: Authors need reader-facing verification after publish.
Application: UX-06 should preserve a clear path from published state to Work Detail or Reading verification.

### Studio Relationship

Studio is the private creation layer.

Why: It is the only core page where higher interaction density is necessary, but it still belongs to Fandom Harbor's brand system.
Impact: The product loop becomes complete: create, publish, discover, read and return.
Application: UX-06 should treat Studio as a creator workspace with different density rules, not as an unrelated admin app.

## 14. UX-06 Implementation Guidance

When UX-06 begins, Studio implementation polish should preserve:

1. Studio as protected creator workspace, not CMS.
2. Work, draft, chapter, metadata, save and publish states as primary hierarchy.
3. Clear draft / published distinction.
4. Honest save feedback and recoverable error states.
5. Deliberate publish flow with reader-facing consequence.
6. Metadata readiness as reader care and archive stewardship.
7. Author identity boundary and public pen-name context where relevant.
8. Reader-facing verification path after publishing.
9. Higher efficiency than reader spaces without dashboard or enterprise drift.
10. Continuity with Homepage, Archive, Author and Reading visual directions.

UX-06 should avoid:

- CMS modules.
- Admin dashboards.
- SaaS analytics panels.
- Notion-like generic workspace metaphors.
- Database-first tables.
- Growth metrics as identity.
- Ambiguous save / publish state.
- Hidden validation until the final step.
- Reader private behavior exposure.
- Any code, token, CSS, component, database or business change outside explicit authorization.

UX-05E does not authorize code changes, token changes, component creation, CSS, Tailwind, Figma file generation, route changes, database changes or business logic changes.

## 15. Chapter Management Visual Guardrail

Future Studio visual exploration must implement the behavior frozen in `../STUDIO_CHAPTER_MANAGEMENT_RULES.md`。

Visual direction:

- The current editing chapter is the dominant work surface。
- Other saved chapters form a quieter collapsible management layer。
- Chapter identity and save / publish state remain scannable without dashboard density。
- Multi-chapter publish selection makes eligible scope and none / partial / all states explicit。
- Select All is an efficiency control，not permission to include unsafe chapters。
- Mobile prioritizes the active chapter and keeps chapter management on demand。

Why: Protected Creator Workspace requires focus and state confidence as chapter count grows。
Impact: Chapter management remains calm and literary while supporting efficient author work。
Application: Future Figma exploration and independently authorized Studio implementation。

This guardrail does not choose a sidebar、drawer、accordion、checkbox component or screen layout。
