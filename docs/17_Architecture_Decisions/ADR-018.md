# ADR-018 — Phase 1C 身份、邀请门禁与手工角色

- Date: 2026-06-29
- Status: Accepted
- Owners/reviewers: Product Owner / Tech Lead
- Related .ai decisions: D-003, D-005, D-011, D-033
- Related requirements/risks: KI-001, KI-006, KI-011, `docs/08_Security/THREAT_MODEL.md`

## Context

Fandom Harbor 必须同时区分 provider identity、进入私域归档的 Membership 和可发布/管理的高权限角色。如果把邀请兑换、JWT metadata 或 Supabase User 对象直接当作业务权限，会导致提权、撤销延迟和 provider 类型渗透。

## Decision

- Phase 1 使用 Supabase Auth email/password 并强制邮箱验证；Magic Link 延后。
- Resend 通过 Supabase Custom SMTP 承载 Auth 邮件，不在应用中增加邮件 SDK。
- Supabase User/Session 在 `packages/auth` 适配为不包含 provider 类型的 Trusted Identity/Session。
- active membership 直接代表 Reader capability。`role_grants` 只保存 Author、Admin 与 Super Admin 的手工、可撤销授权。
- 邀请兑换在 PostgreSQL 原子函数中检查 hash、次数、期限、撤销和重放，仅创建 active membership 与 audit event。
- 敏感授权实时读取 PostgreSQL membership/role grants，服务端工作流与 RLS 同时强制。
- 首个 Super Admin 不通过 migration seed 创建，而由受控、可审计的运维步骤建立。

## Consequences

### Positive

- 邀请入站与高权限授予彻底分离。
- 暂停、撤销和角色变更可在数据库层立即生效。
- 业务合同不依赖 Supabase User/Session，保留未来 provider 迁移边界。
- 邮件交付由 Supabase SMTP 边界管理，应用无需邮件 provider SDK。

### Negative / trade-offs

- 敏感操作需要额外查询当前 membership/role grants，不能只信任长生命 JWT role claim。
- Email/password 需要邮箱验证、密码恢复、频率限制和 SMTP 运维。
- 首个 Super Admin 需要独立运维手册和审计证据。

## Security, data and migration impact

- 用户可编辑 metadata 不用于角色或 Membership 授权。
- 邀请原始 secret 仅在创建时显示，数据库只存 hash；兑换函数防并发与重放。
- `audit_logs` 为 append-only 安全记录，不得向普通成员暴露。
- RLS 测试必须覆盖 Visitor、inactive/active/suspended/revoked member、Reader、Author、Admin、Super Admin 和已撤销 role。

## Verification and review trigger

通过 migration 重建、邀请并发/重放测试、RLS allow/deny 矩阵、角色撤销测试、provider-type 边界测试与审计事件校验验证。

引入 Magic Link/OAuth/MFA、修改邀请能力、使用 JWT role claims、替换 Auth provider/SMTP provider 或改变 Super Admin bootstrap 流程时必须复审。
