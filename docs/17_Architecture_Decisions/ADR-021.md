# ADR-021 — Admin Identity & Access Governance Contract

- Date: 2026-08-16
- Status: Accepted
- Owners/reviewers: Product Owner / Tech Lead
- Related .ai decisions: D-005, D-011, D-033, D-037, D-039
- Related contract: `docs/11_Admin/IDENTITY_ACCESS_GOVERNANCE.md`

## Context

Phase 1C 已建立 active Membership、手工 `role_grants`、capability 派生、RLS 与审计；Admin P0 `/access` 暴露三个可工作的直接写入表单。该界面缺少对象查找、当前状态、Review、幂等和 optimistic concurrency，容易发生错选、重复提交和 stale overwrite。

P1 需要提升治理安全，但不得创建第二套权限真相、扩大现有角色能力、启用 Web 后台入口或使用 Production 进行写入测试。

## Decision

1. Admin P1 定位为 Identity & Access Governance Console，同时治理 Membership 与 Role Grant。
2. 继续以 Auth user ID、active Membership 和 live `role_grants` 为唯一运行期事实；`user_metadata` 与客户端 capability 不参与授权。
3. UI 采用目录/搜索/详情/Review 顺序，服务端和数据库保持独立授权检查。
4. 所有 Mutation 使用规范化原因、二阶段确认、UUID requestId、expected-state 与 `Saved | Unchanged | Conflict` 封闭结果。
5. Admin/Super Admin grant/revoke 及 elevated account Membership 变更必须对当前 actor 执行单次 registration-name/password reauth，并将证明绑定当前 Review payload。
6. reauth 复用既有 Auth provider adapter；不采用 Supabase email/phone nonce reauthentication，不新增 OTP、MFA、Magic Link 或 Auth 架构。
7. P1 暂不采用双人审批；保留最后一个有效 Super Admin 防护、完整原因/Review/reauth/Audit，并接受当前残余风险。
8. 读模型优先 `security invoker` + RLS；必要的原子写函数可使用 `security definer`，但必须空 `search_path`、全限定名、撤销 PUBLIC、最小 execute grant 与函数内 live authorization。
9. 邀请管理延期；Web Admin 入口保持关闭；远程写入 QA 只能使用专用非 Production Supabase 环境。

## Consequences

### Positive

- 避免复制 Membership/Role/capability 权限体系。
- 管理员在写入前能确认真实目标和当前状态。
- 网络重试、双击和 stale Review 不再产生重复或覆盖写入。
- elevated 操作在 Session 权限之外增加当前凭据证明。
- Production 数据与 paused Admin 不再承担开发写入验收。

### Trade-offs

- request ledger、expected-state 与旧 RPC cutover 需要数据库 Migration 和兼容计划。
- 当前不可投递内部 Auth 标识使 Supabase email/phone nonce reauth 不适用；password step-up 必须由应用适配层安全实现。
- 不采用双人审批意味着单一 Super Admin 账号被攻破或误操作仍有残余风险。
- Admin 与 Web 是独立部署与会话边界；未来入口不能假定共享登录状态。

## Rejected alternatives

- 继续保留直接写入表单：缺少目标上下文、Review、幂等与 Conflict，不满足治理要求。
- 在客户端缓存 reauth 布尔值：不能形成可信安全边界。
- 使用用户可编辑 metadata 保存角色或 reauth 状态：存在提权与陈旧声明风险。
- P1 同时加入邀请、内容、审核和分析：范围过大且破坏后续 Phase 所有权。
- 用 Production Supabase 做远程写入 QA：风险不可接受。

## Current Supabase constraints

- [Securing your API](https://supabase.com/docs/guides/api/securing-your-api) 要求 grants 与 RLS 同时控制 Data API 暴露。
- [Database Functions](https://supabase.com/docs/guides/database/functions) 建议优先 invoker；使用 definer 时必须固定 `search_path` 并限制默认 execute 权限。
- [JavaScript reauthenticate](https://supabase.com/docs/reference/javascript/auth-reauthenticate) 通过 email/phone nonce 支持密码变更重认证，不是本项目 Admin password step-up 的现成实现。

## Review triggers

以下任一情况必须复审：新增 role/capability、Auth provider 或 MFA；启用 Web Admin 入口；引入双人审批；管理员规模或合规要求扩大；改变 final Super Admin 保护；允许批量权限操作；修改 Production 测试或 Admin pause/release 策略。
