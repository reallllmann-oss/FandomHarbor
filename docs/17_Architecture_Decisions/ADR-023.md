# ADR-023 — Identity Access Read RPC Authority Boundary

- Status: Accepted — minimal hybrid read authority
- Date: 2026-08-17
- Decision owner: Product Owner
- Related: ADR-008, ADR-021, ADR-022, Admin P1-01, Admin P1-02B

## Decision

Product Owner 选择最小混合权限模型：

1. `search_identity_access_subjects_v1` 使用 `SECURITY INVOKER`。
2. `list_identity_access_audit_v1` 使用 `SECURITY INVOKER`。
3. 只有 `get_identity_access_subject_v1` 可以使用严格受控的 `SECURITY DEFINER`，目的仅为在不开放 private helper 的前提下调用 P1-02A `identity_access_expected_state_snapshot(uuid)` 与 `identity_access_state_token(uuid)`。
4. P1-02A private snapshot/token helpers 继续拒绝 `PUBLIC`、`anon`、`authenticated` 与 `service_role` execute。
5. 不复制 expected-state snapshot/token 算法，不扩大底层表 Grant。

本决定只修正读取权限边界，不授权 Migration、RPC 实现、写入、elevated mutation、KI-033 绕过或远程状态变化。

## Context

P1-01 原设计要求三个 read RPC 全部使用 `SECURITY INVOKER`，同时要求详情 RPC 返回 P1-02A helper 生成的 expected-state token。P1-02A 又有意从全部应用角色撤销 private helper execute。这两项要求在 PostgreSQL nested function 权限语义下不能同时成立。

底层 `profiles`、`memberships`、`role_grants` 与 `audit_logs` 已对 `authenticated` 提供 SELECT，并通过现有 RLS 实时限制为自身或 active Admin/Super Admin 所需范围。因此搜索和 Audit RPC 可继续安全使用 invoker。冲突只存在于详情 RPC 对 private expected-state helper 的嵌套调用。

## Local feasibility proof

在一次性本地 Supabase PostgreSQL 中执行了事务式、最终 rollback 的 probe：

- `authenticated_base_select=true`：四张读取事实表的现有 SELECT grant 存在。
- `authenticated_helper_execute=false`：`private.identity_access_state_token(uuid)` 对 authenticated 保持撤权。
- authenticated 调用临时 `SECURITY INVOKER` wrapper 时得到预期 `insufficient_privilege`。
- `probe_rolled_back=true`：临时 wrapper 未持久化，数据库和仓库文件均未改变。

这证明不能仅依靠 invoker 详情 RPC同时满足“必须使用 P1-02A helper”和“helper 不向 authenticated 开放”。

## Options considered

### Option 1 — Grant authenticated execute on private helpers（rejected）

优点是三个 read RPC 可保持 invoker。缺点是破坏 P1-02A 已冻结的 helper deny 边界，并为应用数据库角色增加一个可直接调用的内部接口。private schema 未暴露 Data API 不能替代 PostgreSQL execute 最小化原则。

### Option 2 — Minimal hybrid authority（selected）

搜索与 Audit 保持 invoker；详情使用一个严格、只读、实时授权的 definer boundary。它保留单一 expected-state 算法和 private helper deny，同时把 privileged surface 限制到一个字段最小化 RPC。

### Option 3 — Duplicate expected-state logic in the detail RPC（rejected）

复制算法会形成两个 token 权威来源，使分页/详情与未来写入的 expected-state 可能漂移，并削弱 P1-02A helper 的单一合同地位。

## Mandatory detail RPC security contract

`get_identity_access_subject_v1` 的未来实现必须同时满足：

- 只读且在 PostgreSQL 合同允许时标记 `STABLE`。
- `SECURITY DEFINER` 与 `SET search_path = ''`。
- 全限定引用所有 schema、table、function、type 与 operator 所依赖的对象；禁止 dynamic SQL。
- 在读取、分类或暴露目标用户之前，先验证 `auth.uid()` 非空。
- 通过数据库实时事实验证 caller Membership 为 active，并存在未撤销的 Admin 或 Super Admin grant；不得依赖 `user_metadata`、客户端 capability 或可能过期的 JWT role claim。
- 未认证使用稳定 authentication error；无权限使用稳定 forbidden error。两者均不得泄露目标是否存在。
- 授权完成后才查询 target；NotFound 仅可返回给已授权 Admin/Super Admin。
- 只返回 P1-01 冻结的最小 Profile、Membership、active grants、effective roles、elevated/唯一 active Super Admin 标识、关键时间与 expected-state。
- expected-state 只能调用 P1-02A `private.identity_access_expected_state_snapshot(uuid)` 和 `private.identity_access_state_token(uuid)`；不得复制或重写算法。
- 不得 INSERT、UPDATE、DELETE、调用写 workflow、写 Ledger/Audit，或改变 Membership、Role、Site Copy 及其他业务数据。

## Execute and grant contract

- 创建详情 RPC 后立即从 `PUBLIC` 与 `anon` 撤销 execute。
- 仅向 `authenticated` 授予详情 RPC execute；不授予 `service_role`。
- P1-02A private helpers 对 `PUBLIC`、`anon`、`authenticated`、`service_role` 的 execute deny 保持不变。
- 不新增或扩大底层表 grant、RLS policy、view 或 exposed schema。
- 搜索和 Audit RPC 继续使用 `SECURITY INVOKER`、空 `search_path`、全限定对象、`PUBLIC/anon` execute deny 与 authenticated-only execute。

## Consequences

- P1-01/P1-02 中“全部 read RPC 为 invoker”的表述由本 ADR 修正为按 RPC 区分的最小混合模型。
- 未来 P1-02B 实现必须用 catalog、允许/拒绝矩阵与 read-before/read-after 证明详情 definer 无越权和零写入。
- elevated account 仍仅可按最小字段读取；本 ADR 不创建任何 elevated mutation 能力。
- KI-033 仍为 `ACCEPTED DEFERRED BOUNDARY`，技术问题未解决；ADR-022 Option 3 保持不变。
- P1-02B 实现、Migration、SQL、远程 QA 与后续阶段仍需独立 Product Owner 授权。
