# ADR-025 — 真实邮箱认证、邀请码预留与存量身份迁移

- Date: 2026-10-14
- Status: Proposed — Product Owner approval required
- Owners/reviewers: Product Owner / Tech Lead / Security reviewer
- Related .ai decisions: D-003, D-005, D-011, D-037, D-039, D-040
- Related requirements/risks: V1 Package A A1/A2；KI-009、KI-011；ADR-003、ADR-008、ADR-020、ADR-021、ADR-022、ADR-024
- Supersedes when accepted: ADR-020 的不可投递邮箱、关闭 Email Confirmation 及无恢复通道部分

## Context

ADR-020 为有限邀请制 Beta 选择了“注册名 + 密码 + 邀请码”，并将规范化注册名派生为
`@accounts.fandom-harbor.invalid` 内部 Auth 标识。该方案使注册事务不依赖邮件，但没有真实邮箱验证、密码恢复、邮箱变更或安全联系通道。

正式 V1 已确认以下新要求：每个账号绑定一个真实且已验证邮箱；登录仍以注册名和密码为主；未验证新账号不得获得 Reader、Author 或 Admin 能力；邀请码不得因邮件失败或流程中断被永久消耗；所有已有 Auth UID、Membership、角色、内容、TOTP 因子和审计关系必须保留。

当前代码使用 `@supabase/supabase-js` `2.108.2`、`@supabase/ssr` `0.12.0`。仓库内本地安全基线保持 `enable_confirmations=false`，但已经版本化 6 位、15 分钟 OTP、`secure_password_change=true` 和中文 confirmation/recovery/email-change 模板；Custom SMTP 与 Production Email Confirmation 仍未配置或启用。

本 ADR 只是一份待批准设计。它不授权 Migration、Production Auth 设置、SMTP、用户身份、角色或 Session 修改。

## Decision drivers

- Supabase Auth 继续作为唯一密码和 Session 签发系统；不建立第二套密码数据库。
- 用户界面保留“注册名 + 密码”登录。
- 真实邮箱只存在于受保护的 Supabase Auth 身份边界；当前登录用户的原生 JWT / SSR Session 可包含本人 email claim，但不得进入公开 Profile、作者页、作品、搜索、其他用户响应、URL、应用日志或 Audit metadata。
- 邀请码并发安全不得弱于现有 `FOR UPDATE`、唯一约束和事务触发器。
- 授权继续只依赖 Auth UID、active Membership、`role_grants` 和服务端验证的可信 Auth claims。
- 存量迁移必须原地更新同一个 Auth user；禁止删除重建、换 UID 或重挂角色/作品。
- Super Admin 邮箱迁移不得降低 P1-07C 已验收的 TOTP/AAL2、fresh TOTP、Session binding 和双人冗余。

## Options considered

### Option A — Supabase Auth 真实邮箱 + 服务端注册名登录代理（推荐）

`auth.users.email` 成为唯一真实邮箱事实源。`profiles.registration_name` 继续作为公开注册名。登录 Server Action 在服务器侧用注册名解析 Auth UID，再使用仅服务器持有的 Supabase secret key 调用 Auth Admin `getUserById` 取得邮箱，最后用普通 publishable-key SSR client 执行 `signInWithPassword(email, password)`。

优点：复用 Supabase 密码、邮箱确认、恢复、邮箱变更、Session 与 MFA；保留用户名登录；不复制真实邮箱。代价：Web 服务器新增一个高权限 secret boundary，必须限制在单个 `server-only` 模块并接受独立轮换、脱敏和审计。

### Option B — 用户改为邮箱 + 密码登录

技术最简单，但违反已经确认的用户名登录体验，不采用。

### Option C — 自建用户名密码验证或密码镜像

会形成第二套 credential store、密码散列与恢复系统，不采用。

### Option D — 继续把不可投递邮箱作为 Auth 主邮箱，另存联系邮箱

Supabase 原生确认、恢复和安全邮箱变更仍无法围绕联系邮箱工作，会重复建设验证系统，不采用。

## Decision

### 1. 身份模型

1. `auth.users.id` 继续是唯一稳定身份主键。
2. `auth.users.email` 是唯一真实邮箱事实源；Auth 自身的邮箱唯一约束执行“一邮箱一账号”。
3. `profiles.registration_name` 继续是登录名和站内显示身份，不保存邮箱。
4. 新增数据库拥有的 `canonical_login_name(text)` 契约和 `login_name_claims`（或等价单表唯一声明）。规范化顺序固定为 NFKC → trim → 数据库 `lower`，数据库函数是唯一权威实现；应用层只做 UX 预检，登录、预留、回填和唯一约束全部使用数据库返回的 `login_name_key`。既有 `profiles.registration_name` 保留为显示值，普通用户不得借此读取其他账号邮箱或 UID。
5. 新增无 PII 的账号安全状态记录，至少区分：
   - `legacy_unbound`：仍使用 `.invalid` Auth 邮箱；
   - `verification_pending`：新注册或存量邮箱绑定尚未完成；
   - `verified`：真实邮箱已由 Supabase Auth 确认；
   - `migration_conflict`：邮箱唯一性或迁移核对失败，需要人工处理。
6. 真实邮箱不复制到 Profile、Membership、Invitation、Audit log 或 `user_metadata`。Audit 只记录 Auth UID、reservation ID、invitation ID、状态和非敏感原因码。

### 2. 服务端用户名登录

登录流程固定为：

1. Server Action 接收注册名并执行应用级 IP + 注册名 fingerprint 限流；应用层规范化结果不作为授权或唯一性依据。
2. 服务器专用 Supabase secret client 调用只授予 `service_role` 的解析 RPC；RPC 使用数据库 `canonical_login_name(text)` 查询唯一 `login_name_claims`，只返回 Auth UID。
3. 使用 Auth Admin `getUserById` 在服务器内取得当前 Auth email。
4. 使用普通 publishable-key SSR client 调用 `signInWithPassword`，让 Supabase Auth 校验密码并签发用户 Session。
5. 不存在的注册名走等价的 decoy Auth 请求或时间均衡路径；所有失败统一返回“注册名或密码错误”。
6. 登录代理解析出的 email、密码、secret key、完整 Auth error 和 Admin Auth user object 不进入业务响应、URL、analytics 或应用日志。Supabase 原生 Session/JWT 包含当前用户本人 email claim 属于已接受的 provider-native 行为，不为此另建自定义 Session。

解析 RPC 默认 revoke `PUBLIC`、`anon`、`authenticated`，不得成为公开的“注册名是否存在”查询。现有 `lower(registration_name)` 唯一索引升级前必须先运行 NFKC/case 冲突盘点；存在冲突即 Stop Gate，不自动改名或合并账号。跨 JavaScript/PostgreSQL 的固定 Unicode fixture 必须证明预检与数据库结果一致，但数据库结果始终优先。

服务器 secret key 采用可独立轮换的 `sb_secret_...` key，不新增 legacy `service_role` key。它只进入 Vercel server environment 的单个 `server-only` 模块；任何 `NEXT_PUBLIC_`、Client Component、Browser bundle、错误响应和测试快照都不得引用。该 client 只允许调用登录解析 RPC 和 Auth Admin `getUserById`，不得作为普通业务 repository 的通用 client。

#### 2.1 本人 Session 与公开数据边界

- 当前登录用户可在 Supabase 原生 Auth Session/JWT 中访问自己的 email claim；保留 `@supabase/ssr` Cookie 与 Session 刷新机制，不额外建立 opaque Session 层。
- 公开 Profile、作者页、作品、搜索、普通 Data API 和其他用户响应不得投影真实邮箱。普通 `anon` / `authenticated` 角色不得执行用户名→UID 解析 RPC，也不得通过其他 RPC 查询他人 Auth email。
- 含认证状态或 Session 的页面、Server Action 与响应不得进入跨用户共享缓存；当前 B2 认证页面使用动态渲染，本地响应验证为 `Cache-Control: no-cache, must-revalidate`。
- Session Token、Refresh Token、密码、OTP、邀请码、registration proof 和服务端 secret 不得进入应用日志、analytics、错误响应、测试快照或公开缓存。
- 授权继续使用可信 Auth UID/claims、active Membership、`role_grants` 和 RLS；敏感操作继续执行最新 Session、AAL2/fresh TOTP 等现有 P1-07C 约束。

### 3. 新账号邮箱验证

1. 注册表单收集注册名、真实邮箱、密码和邀请码。
2. Server Action 使用 server-only secret client 调用 `prepare_registration_attempt`。该函数在事务 T1 中锁定 invitation、核对容量与撤销/过期状态、声明唯一登录名，并创建 2 小时 reservation、短期 registration attempt 和数据库预分配的随机 Auth UUID v4；此时不创建 Auth user、Profile、Membership、Redemption，也不增加 `use_count`。
3. T1 返回预分配 UID 和至少 256-bit CSPRNG、一次性的 attempt proof。数据库只保存 `SHA-256(proof)`、proof/email binding 与 `SHA-256(canonical_auth_email || NUL || expected_auth_user_id)`；不保存明文 proof 或业务表邮箱。proof 只用于受保护的 T1 状态、重试和释放操作，保存在短期 `HttpOnly + Secure + SameSite=Lax` opaque attempt cookie 和当前服务器内存；**不得传给 GoTrue metadata、Auth identity、浏览器 Auth 对象或 Session**。
4. 同一 Server Action 通过单个 `server-only` 高权限边界调用 Auth Admin Create User，显式提交 T1 预分配 UID、真实邮箱、密码和 `email_confirm=false`，且 `user_metadata` 为空。随机 UID 不是单独的授权凭据；安全结论同时依赖 server secret、私有 attempt 行、邮箱+UID binding、状态/时间谓词和 Auth insert trigger。普通客户端不能在公开 Signup API 中指定 UID。
5. PostgreSQL `Before User Created` Hook 在 `email_required` mode 只负责 fail-closed 拒绝普通公开 Signup；真实 GoTrue `v2.191.0` 验证表明 Admin Create User 不执行该 Hook。因此 Hook 不读 attempt/proof、不持久 claim，也不被描述为 T2 原子写入的一部分。
6. `auth.users BEFORE INSERT` trigger 在 Auth 数据库事务 T2 内按 `NEW.id` 锁定私有 attempt/reservation/invitation，重新核对预分配 UID、Auth email binding、proof/attempt 短期窗口、2 小时 reservation、邀请码撤销/到期和 login-name claim，再用状态谓词 `UPDATE ... RETURNING` 一次性 claim。`auth_user_id` 外键保持 `DEFERRABLE INITIALLY DEFERRED`，不得删除或放宽；失败、竞争、重复 UID 或邮箱不匹配全部回滚并返回通用拒绝。
7. `auth.users AFTER INSERT` trigger 只接受同事务已 claim 的 attempt，创建 Profile、`pending` Membership 和账号安全状态，并将 login-name claim 从 attempt 转为 UID；不得创建 Redemption 或增加 `use_count`。任何 AFTER trigger 写入失败必须连同 Auth user 与 BEFORE claim 一起回滚。
8. Admin Create User 本身不会投递确认邮件。创建成功后由受控服务器调用 Supabase 原生 `resend({ type: "signup" })` 触发中文确认邮件；`generateLink(type: "signup")` 可生成原生确认凭据但不会自动发信，且会影响 resend 冷却计时，不作为普通注册投递路径。
9. Email Confirmation 开启后，Auth user 仍为 unconfirmed 且 Membership 为 pending。中文确认邮件使用 Supabase 模板 `{{ .Token }}` 发送 6 位 OTP；验证码页面通过 Supabase `verifyOtp` 完成确认。
10. OTP 验证导致 `auth.users.email_confirmed_at` 首次从 null 变为非 null 时，数据库触发器在单一事务 T3 中锁定 reservation/invitation，消费仍有效的预留、写 Redemption、增加 `use_count`、激活 Membership 并写 Audit。
11. OTP 验证成功但 reservation 已过期或邀请码已撤销时，账号保持已验证但 Membership 仍为 `pending`；任何 Auth Session 都不等于站内授权，用户必须提交新的有效邀请码后才获得 Reader/Author 能力。

验证码建议有效期 15 分钟；邀请码预留期固定为 2 小时。两者独立：重发验证码、刷新页面、重新登录和发送失败重试都不得延长预留时间。

数据库必须使用受控的 registration mode 区分 Beta legacy signup 与 V1 email-required signup，不能信任客户端可写的 `user_metadata` 选择安全路径。在 `email_required` mode 下，Before User Created Hook 拒绝公开 Signup，Auth insert trigger 只接受与私有 prepared attempt 的 expected UID 和邮箱 binding 精确匹配的未确认 Admin 创建，因此持有 publishable key 的调用者不能绕过 Server Action 直接注册。Production cutover 时先暂停新注册，再切换数据库 mode、Hook、Email Confirmation、SMTP/模板并完成 smoke，最后恢复注册；任何中间状态都不得允许 `.invalid` 新账号或无邀请账号绕过验证。

#### 3.1 事务边界、补偿与幂等

- T1（业务数据库）：原子完成 expected Auth UID、attempt、login-name claim 和 reservation。T1 与 Auth Admin Create User 不是同一事务，不得写成“预留与 Auth 创建原子完成”。
- T2（Supabase Auth 创建）：Admin endpoint 发起 GoTrue 创建；`auth.users BEFORE INSERT` claim、Auth user/identity insert 与 AFTER INSERT 的 Profile/pending Membership/account-security 写入必须在同一数据库事务中提交或回滚。Before User Created Hook 对 Admin Create 不执行，只承担公开 Signup 的独立拒绝边界。
- 邮件投递发生在 T2 提交之后且不属于数据库事务。即时 SMTP 失败保留 2 小时 reservation，允许安全重发；绝不激活 Membership 或消费 invitation。
- Admin Create 明确失败且能证明未创建 Auth user 时，Server Action 调用幂等 release 函数，释放 reservation 和 login-name claim。网络超时或结果不明时不得立即释放；先按 attempt ID 查询受保护状态，`auth_created` 转 resend，仍为 `prepared` 才可在受控确认后释放，否则等待 2 小时自然失效。
- 已存在邮箱、重复 UID 或模糊网络结果都不能依据 Admin API 文案改变 invitation。服务器只信任私有 attempt 状态；对外使用统一响应，避免邮箱或注册名枚举。
- 重复提交携带同一 opaque attempt cookie 时复用原 attempt、相同 expected UID 和原 reservation，不创建第二个 reservation。proof 轮换只更新短期 T1 控制凭据，不延长 reservation；重复 Admin Create、insert trigger、OTP 和 activation 均返回既有结果或通用拒绝，不重复计数。
- 过期正确性不依赖 cron。所有容量和状态查询按 `expires_at` 即时排除过期 reservation；sweep 仅显式写 `expired` 与 Audit。

### 4. 邀请码预留状态机

新增 `invitation_reservations`，状态为：

- `reserved`：占用一个剩余名额，但尚未增加 `use_count`；
- `consumed`：邮箱已验证，已生成 Redemption 并增加 `use_count`；
- `released`：主动取消、邀请撤销或安全拒绝；
- `expired`：超过 reservation expiry。

推荐转换：

```text
注册申请
  -> 锁定 invitation 行
  -> 校验 revoked / invitation expiry / use_count + active reservations
  -> T1 创建 expected Auth UID + 2h reserved + attempt + login-name claim
  -> T2 Auth Admin Create User（空 user_metadata）
       -> BEFORE INSERT 按 expected UID + email binding 一次性 claim
       -> AFTER INSERT 创建 Profile + pending Membership
  -> Before User Created Hook 独立拒绝普通公开 Signup
  -> 邮箱验证（T3）
       -> 有效 reservation：同事务 consumed + redemption + use_count + active
       -> reservation 过期：邮箱 verified，Membership 保持 pending，等待新邀请码
  -> 取消、撤销或超时：released/expired，不增加 use_count
```

并发规则：

- 预约和消费都先对 invitation 执行 `FOR UPDATE`；同一邀请码的名额判断被串行化。
- 容量为 `use_count + 未过期 reserved 数量 < max_uses`。
- 每个 registration attempt / Auth UID 同时最多一个 active reservation；每个 reservation 只能消费一次。
- reservation expiry 固定为 `least(created_at + interval '2 hours', invitation.expires_at)`，不越过邀请码本身有效期。
- 正确性不依赖 cron：所有容量查询立即忽略已过期 reservation。后台 sweep 只负责把历史状态显式更新为 `expired` 并补 Audit。
- resend 不新建 reservation、不改变邀请码、不延长 expiry。
- activation RPC/trigger 必须幂等；重复验证或网络重试返回既有结果，不重复计数。
- 任意 Profile、Membership、Reservation、Redemption、counter 或 Audit 写入失败时整个数据库事务回滚。
- 邀请码在 reservation 期间被撤销时，默认不得继续激活，并在下一次状态检查时释放。若 Product Owner 希望既有 reservation 获得宽限，必须在批准本 ADR 前明确改变此规则。

防恶意占用：prepare、Admin Create 编排、重发、恢复端点启用 IP + email/注册名/invitation fingerprint 分层限流；连续失败触发 Turnstile；同一浏览器使用 opaque attempt cookie；OTP、proof 和 invitation 明文不进入数据库或日志，proof 绝不进入 GoTrue metadata；expired reservation 不占容量。尚未创建 Auth user 的过期 attempt 可原子释放 login-name claim；已经创建 Auth user 的注册名不得自动转给他人，也不得删除 Auth UID，必须进入恢复或人工处理路径。

### 5. 密码恢复、修改密码和邮箱变更

- 忘记密码页面接受注册名并始终返回相同成功文案。服务器解析邮箱后调用 Supabase `resetPasswordForEmail`。Recovery 模板使用 6 位 OTP；验证使用 `verifyOtp(..., type: "recovery")`。验证成功后只签发 10 分钟、绑定 Auth UID 的 HMAC 恢复授权 Cookie；`updateUser` 仅在该授权有效或当前密码重新验证成功时设置新密码。普通布尔 Cookie 不得作为恢复授权事实。
- 修改密码要求当前密码或 Supabase reauthentication nonce；开启 `secure_password_change`。成功后发送中文安全通知，并撤销其他 Session。
- 已绑定真实邮箱的常规邮箱变更使用 Supabase `updateUser({ email })`、Secure Email Change 和旧/新邮箱双确认。不得使用 Admin API 直接把任意新邮箱标记为已确认。
- 邮箱和密码恢复入口必须保持防枚举文案、统一 HTTP 行为、限流与 CAPTCHA。
- 退出或 Session 撤销后，短期 access token 仍可能在 JWT expiry 前有效；敏感 Admin/Super Admin 操作继续验证 `session_id`、AAL2 和 fresh TOTP，不依赖 email claim。

### 6. 存量账号原地迁移

#### Reader / Author

1. 用户继续使用注册名 + 现有密码登录 `.invalid` 身份。
2. 绑定前要求一次新的当前密码校验，并核对当前 Session 的 UID；生成短期、单 UID、单 `session_id`、单目标 email fingerprint 的 binding operation，但不改变 UID、Membership 或角色。
3. 使用 Supabase 原生 Secure Email Change 的 current/new 两臂为同一个 Auth user 完成变更；旧 `.invalid` 地址不可投递，因此 current arm 由服务器在完成替代当前身份凭据证明后处理，new arm 必须由新邮箱持有人完成。
4. 两臂完成前，旧 `.invalid` email 仍是 Auth 主邮箱，用户名登录代理继续动态取得它，旧登录不中断；绑定 operation 的 pending/failed 状态不能改变 Membership 或内容权限。
5. 两臂完成后，`auth.users.email` 和 email identity 原地切换；UID、password hash、Profile、Membership、Role Grant、作品归属与关系表必须保持不变。
6. 服务器登录代理下一次自动取得新邮箱，用户仍输入注册名 + 密码。成功后 global sign-out，清除旧 Session 与 recovery/reauth 上下文，并要求重新登录；Author 再核对草稿和作品 owner UUID。

`.invalid` 旧地址不可接收 Secure Email Change 的 current-email 消息，因此存量绑定不能直接套用普通双邮箱 UI。推荐实现一个仅用于 legacy account 的原生 token 编排器：

- 用户先以现有密码对当前 `.invalid` identity 重新执行 `signInWithPassword`，并核对返回 UID 等于当前 Session UID；Admin/Super Admin 还必须满足 AAL2、fresh TOTP 和既有 P1-07C session binding。
- 服务器使用 Supabase Admin `generateLink` 的 `email_change_current` / `email_change_new` 生成原生两臂。精确调用顺序、两臂确认状态和 token expiry 必须由与 Production Auth 版本及配置相同的隔离项目锁定为 contract test。
- current arm 的 credential 只在服务器内存中存在，并且只能在上述 fresh credential 通过后由无持久 Session 的服务器 Auth client 提交；不得发送到 `.invalid` 地址、浏览器、队列或日志。
- new arm 由 migration-only sender 通过已经验收的 Preview 邮件基础设施发送 6 位原生 `email_otp`；用户提交后，服务器以新邮箱 + OTP + `type: "email_change"` 交给 Supabase Auth 验证。应用不签发自定义邮箱所有权 token，也不存密码或原生 token。
- operation 状态只记录 UID、目标 email 的 keyed fingerprint、arm 状态、expiry、attempt count 和原因码，不记录真实邮箱、OTP、action link、token hash 或 current password。

`generateLink` 只生成 Supabase 原生凭据，不会通过 Custom SMTP 自动发信；migration-only sender 只负责投递 new-arm 原生 OTP，必须使用独立 server credential、禁止日志记录 token，并与普通 Auth SMTP 模板分开验收。Supabase Auth open issue #2538 记录 `email_change_new` 响应中的 `properties.hashed_token` 可能按旧邮箱计算、与实际存储 token 不一致，而 `properties.action_link` 中的 token 来自实际存储值。故实现不得信任 new-arm `properties.hashed_token`；首选传递 `properties.email_otp`，并由 `verifyOtp({ email: newEmail, token, type: "email_change" })` 验证。若改用 action link，只能解析和 POST 其中 token，不得让邮件扫描器 GET 即消费。两条路径都必须在隔离项目实证，不能由文档假定。

B3 必须覆盖以下版本锁定矩阵：Secure Email Change 开启、Email Confirmation/`mailer_autoconfirm` 与 Production 目标一致；分别验证 current→new 生成/确认顺序、OTP 与 action-link token、错误/过期/重放、同邮箱冲突、Session 变化，以及两臂后的 `auth.identities`。任何一项不能稳定复现即 Stop Gate；禁止以 `updateUserById({ email, email_confirm: true })`、直接修改 `auth.users` token 列或关闭 Secure Email Change 绕过新邮箱所有权验证。

#### 失败、恢复与回滚

- 两臂均未完成：binding operation 可幂等取消/过期，旧 `.invalid` email、UID、密码和登录路径不变。
- current arm 已完成但 new arm 未完成：旧邮箱仍必须保持主邮箱。用户可在 operation 有效期内重发 new-arm OTP；到期后先在隔离项目证明 Supabase pending change 的安全失效/重启方式。没有受支持的清理路径时不得直接改 Auth 内部列，升级为人工恢复并停止该批次。
- new arm 验证失败、邮件退信或目标邮箱冲突：保持旧身份可登录，统一对外错误，状态记为 `migration_conflict` 或可重试失败；不透露目标邮箱是否属于其他账号。
- 两臂成功后：不自动回写 `.invalid`。如连续性核对失败，立即停止后续账号、global sign-out 并进入同 UID 事故恢复；禁止删除重建、自动合并或转移角色/内容。
- B3 只允许合成账号和隔离项目。真实 Reader/Author/Admin/Super Admin 迁移必须由独立 Production 授权、逐批 Stop Gate 和可恢复快照覆盖。

#### 冲突和过渡

- 同一真实邮箱只能绑定一个 Auth user。发生冲突时两个账号都不得自动合并、删除或换 UID；状态转为 `migration_conflict`，由 Product Owner/安全运营核验归属。
- 未完成迁移账号在过渡期继续使用旧注册名 + 密码登录，但没有邮件恢复能力。过渡截止日前显示中文安全提示。
- Production 获批后的迁移顺序为 Super Admin（逐人）→ Admin（逐人/小批）→ Author/Reader 分批；新账号真实邮箱注册的 Preview 验证与存量 Production 迁移相互独立，不以真实用户试迁移作为上线测试。
- 截止策略（Reader 是否降为只读、Author 是否暂停发布）需要 Product Owner 单独决定，不能在代码中默认为封禁。

### 7. Super Admin 身份保护

Super Admin 采用独立变更窗口，不走批量自助迁移：

1. 记录两名受控 Super Admin 的非敏感前置清单：Auth UID、active Membership、active roles、verified TOTP factor ID/status/count、当前 migration 数和未消费 elevated intent 数；不记录 secret、QR 或 OTP。
2. 先迁移次要 Super Admin；另一名保持原状并可执行紧急治理。
3. 迁移者必须以现有密码登录，并完成 fresh TOTP/AAL2；legacy current-arm 只能绑定该 verified session、UID、目标 email fingerprint 和短期 operation ID。
4. 新邮箱确认后执行 global Session rotation；旧 Session 和旧 P1-07C elevated intent 不得复用。
5. 重新以注册名 + 密码登录、完成 TOTP challenge，验证相同 UID、相同两个 verified TOTP factors、AAL2、protected Admin read、role ledger 与 denial boundary。
6. 第一名完全 PASS 后才迁移第二名。任何 UID、factor、Membership、role、Session binding 或 Audit 差异立即停止。

邮箱迁移不修改 `auth.mfa_factors`、`role_grants`、Membership 或 P1-07C functions。P1-07C Migration D 和 commissioning 不重跑；只运行专门的身份连续性回归。

### 8. 正式邮件服务

Production 必须使用 Custom SMTP；Supabase 默认邮件服务只适合测试，且默认额度和模板能力不满足正式 V1。

推荐首选 Resend 的 Supabase SMTP integration；Postmark transactional SMTP 为可替代方案；AWS SES 适合需要更高规模、但愿意承担 sandbox、IAM 和运维复杂度的阶段。最终供应商由 Product Owner 决定。

要求：

- 使用独立发送子域，例如 Preview `preview-auth.fandomharbor.com`、Production `auth.fandomharbor.com`。
- 按供应商给出的记录完成 DKIM、aligned SPF/Return-Path；域级 DMARC 先 `p=none` 收集报告，再在误投率可接受后升级 `quarantine/reject`。
- 不创建第二条互相冲突的 SPF TXT；DNS 值以选定供应商当时控制台为准，不写死在仓库。
- Auth 邮件关闭 link/open tracking，避免改写一次性链接；验证码邮件不得包含营销内容。
- Preview 与 Production 使用独立项目、SMTP credential、sender、额度和告警；credential 只进入平台 Secret Manager。
- 中文模板覆盖 signup confirmation、recovery、email change、reauthentication、password changed、email changed、MFA factor added/removed。
- UI 对即时发送失败显示可重试的通用中文提示；异步 bounce/complaint 由供应商 suppression、dashboard/webhook 和运营告警处理，不向匿名请求者确认账号是否存在。
- 建议基线：同一操作 60 秒内不可重发；每个账号与 IP 的小时额度；异常后 Turnstile；实际 Supabase 和供应商额度在 Preview 压测后批准。

### 9. B1-R3 本地验证证据（不构成 Production 批准）

在本地 Supabase / GoTrue `v2.191.0`、合成账号和 Mailpit 中已验证：

- Admin Create User 接受并保留数据库预分配 UUID，`email_confirm=false` 时建立 unconfirmed Auth user；Admin Create 不自动发信。
- Admin Create 不执行 Before User Created Hook；公开 Signup 在 `email_required` mode 被 Hook 拒绝，携带旧 proof metadata 也不能 claim attempt。
- `auth.users BEFORE INSERT` 按 expected UID + email binding 一次性 claim；错误邮箱失败，同 UID 并发 Admin Create 仅一个成功。
- `auth.users AFTER INSERT` 建立 Profile/pending Membership；故障注入和后续 BEFORE trigger 故障均使 Auth user、claim、Profile、Membership 整体回滚。
- 新路径不向 GoTrue metadata 传递 proof；`auth.users.raw_user_meta_data`、`auth.identities.identity_data`、Admin Create/Read/Update 响应、getUser、Session 和 JWT 均未发现 transport credential。普通 metadata 更新仍保留。
- `generateLink(type: "signup")` 对已有 unconfirmed user 返回成功但不投递邮件；等待本地 resend 冷却后，原生 signup resend 投递至 Mailpit 并完成真实 Auth 确认。
- reservation 有效时，真实确认在 T3 原子完成 Redemption、`use_count + 1` 和 Membership active；故障注入完整回滚，重复激活不重复消费。
- 通过受控时钟将 reservation 推至过期后，真实 Auth 确认保持 Membership pending、原 invitation `use_count=0`；登录后提交新邀请码可按恢复路径激活。
- 两连接最后名额竞争只有一个 reservation；2 小时硬边界、邀请码提前到期、撤销、proof 轮换不续期、过期不占容量的 SQL 回归通过。
- `apps/web/src/lib/server-registration.ts` 提供唯一最小 `server-only` broker：调用者不能提交 UID；邀请码在服务器内哈希；secret 只用于 prepare/status/release 和 Admin Create；resend 只使用 publishable key；返回值不含 UID、email、proof、invitation 或 Auth user。明确 Admin 拒绝且私有状态仍为 prepared 时幂等 release，网络结果不明时不释放并等待状态恢复/硬 expiry。
- broker 尚未暴露为浏览器可调用的 Server Action，也未接入 legacy 注册表单；B2 必须在加入 opaque HttpOnly attempt cookie、限流/防枚举和真实邮箱 UI 后才能启用。`email_required` 数据库 mode 在此之前仍能拒绝当前公开 Signup 路径。

以上证明 B1 本地可行性；不构成 Production Migration 批准。ADR 状态继续为 Proposed。

### 9.1 B2 本地验证证据（不构成 Preview/Production 邮件批准）

在同一隔离环境中已经完成 B2 应用层接线和真实 GoTrue/Mailpit 验证：

- 注册表单、Server Action、B1 broker 与 `HttpOnly + SameSite=Lax` opaque attempt Cookie 已接通；浏览器不能提交 expected UID，公开 Signup 在 `email_required` mode 仍被拒绝。
- Fandom Harbor 中文 confirmation、recovery、email-change 模板由 GoTrue 实际加载，均包含原生 6 位 OTP；未出现默认英文正文、服务端 secret 或 transport proof。
- 页面刷新、即时重发拒绝和后续合法重发均不改变原 2 小时 reservation；错误、过期和重放 signup/recovery OTP 均被真实 Auth 拒绝。
- 真实邮箱确认驱动 T3 从 pending 原子激活；未验证账号不能进入 Author capability 路径；Redemption 和 invitation counter 不重复写入。
- 注册名登录代理同时通过 real-email 与 legacy `.invalid` 合成账号验证；页面、Server Action 返回、普通 RPC 和客户端 bundle 未出现 resolver 返回的邮箱或 Admin secret。`@supabase/ssr` 的标准用户 Session Cookie 包含登录用户本人 email claim；Product Owner 于 2026-10-15 正式接受该 provider-native 行为，不引入自定义 Session。该接受不放宽公开数据、跨账号响应、缓存、日志或凭据边界。
- 忘记密码使用统一响应；Recovery OTP 可更新密码，旧密码失效。恢复授权采用 UID-bound、10 分钟 HMAC Cookie；伪造、跨 UID 和过期授权被拒绝，成功后撤销其他 Session。
- 已验证真实邮箱账号的 Secure Email Change 旧/新邮箱双 OTP 流程通过，Auth UID 与 login-name binding 不变；legacy `.invalid` 绑定仍严格保留给 B3。
- B2 server-only RPC 仅授予 `service_role`，rate-limit 表启用 RLS 且只保存 HMAC subject digest；所有 `SECURITY DEFINER` 固定空 `search_path`。
- 2026-10-15 最小隐私增量检查确认：`public` schema 无 email-like 列，无引用 email 或 `auth.users` 的公开 view；匿名 Profile Data API 与 service-only login resolver RPC 均返回 401；可执行的 legacy invitation RPC 不返回邮箱。认证相关页面为动态响应且实测 `no-cache, must-revalidate`；相关运行时模块无凭据日志或 analytics 调用，最小本地请求日志只含路径、状态与耗时。
- Web 122 项、Auth 41 项、Database 161 项测试、B2 pgTAP、TypeScript、ESLint 和 Production build 通过；数据库 lint 只有三个既有非 B2 warning。原有 own-session email claim 检查保留为明确证据，现按 Product Owner 决策标记为“本人 Session 允许”，不得用于推导公开或跨账号邮箱可见。
- 测试结束后 registration mode 已恢复 `legacy`，Email Confirmation 已恢复关闭，GoTrue `AUTOCONFIRM=true`，Auth metadata/identity 的 transport key 计数为零。

B2 在当前授权范围内判定为 **PASS — LOCAL / NON-PRODUCTION**。该结论不代表外部邮件、Preview 或 Production 已上线，也不代表 ADR-025 已 Accepted。B4a 的 Preview Custom SMTP、DNS/DKIM/SPF/DMARC、供应商额度/退信与 CAPTCHA/运营监控，以及 B3 的存量 UID/TOTP 迁移仍是独立 Stop Gate。

### 10. Threat model and mitigations

| Threat                           | Mitigation                                                                                                                                                              |
| -------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 注册名/邮箱枚举                  | 统一响应、统一跳转、时间均衡、匿名接口不返回 email/UID/存在性                                                                                                           |
| 暴力密码与 OTP                   | Supabase rate limits、应用级 IP + account fingerprint 限流、短 expiry、Turnstile、告警                                                                                  |
| 邀请码名额恶意占用               | 2h hard expiry、resend 不续期、单 attempt/UID 单 reservation、每 IP/email/注册名/邀请码分层限流、expired 不计容量                                                       |
| 并发超售或重复消费               | invitation `FOR UPDATE`、唯一约束、单事务 consume、幂等 key 和并发 SQL 测试                                                                                             |
| 绕过 Web 直调 Auth Signup        | DB 受控 mode；PostgreSQL Before User Created Hook 默认拒绝公开 Signup；Admin 创建仅在 server-only secret boundary；insert trigger 要求私有 expected UID + email binding |
| 伪造或重放 `user_metadata`       | 新流程不传 transport proof 或 attempt metadata；insert trigger 显式拒绝废弃内部键；授权只来自私有 attempt、UID/email binding、状态与锁                                  |
| 真实邮箱泄露                     | 仅存 Auth schema；本人原生 Session/JWT claim 允许；不进入公开 Profile/作者/作品/搜索/他人响应/user_metadata/Audit；server-only lookup；日志、analytics 和共享缓存脱敏   |
| server secret 泄露               | 独立 `sb_secret_...` key、仅服务器环境、禁止 Client import、定期轮换、secret scan、最小模块                                                                             |
| Email change 账号接管            | fresh password/reauthentication；普通账号双邮箱确认；legacy 新邮箱原生 token；高权限再要求 AAL2/fresh TOTP                                                              |
| JWT/Session 在撤销后短时继续可用 | 合理 JWT expiry；敏感操作核对 `session_id`、AAL2、fresh TOTP；邮箱/密码改变后 Session rotation                                                                          |
| 邮件扫描器或 tracking 消耗链接   | 以手输 OTP 为主；关闭 click/open tracking；如使用链接则先到应用确认页再 POST verify                                                                                     |
| 存量迁移 UID/TOTP 丢失           | 同 UID 原地变更；迁移前后 inventory；一名 Super Admin 一次；另一名保持可用；差异即 Stop Gate                                                                            |
| 邮箱冲突导致错误合并             | Auth unique constraint；状态转 conflict；禁止自动 merge/delete/role/content transfer                                                                                    |

## Consequences

### Positive

- 保留注册名体验，同时获得 Supabase 原生邮箱确认、恢复、安全变更、Session 和 MFA。
- 邀请名额只在验证成功时正式消费，邮件失败不会永久浪费邀请。
- 现有 UID 作为所有关系的主键，作品、角色和审计无需重挂。
- 邮箱留在 Auth 边界，普通 RLS/API 查询不会得到其他用户邮箱。

### Negative / trade-offs

- Web server 新增 secret key，泄露会绕过 RLS；必须最小化模块、权限面、日志和轮换窗口。
- T1 reservation 与 T2 Auth Admin 创建是明确的跨事务流程；T2 内 `auth.users` BEFORE/AFTER triggers、Auth identity 和业务写入的回滚语义需要真实本地 Auth 与隔离 Preview 验证。
- 存量 `.invalid` 地址无法正常完成旧邮箱确认，legacy token 编排是一次性高风险迁移边界。
- 邮件投递、DNS、bounce 和供应商容量成为上线依赖。
- Supabase email-change Admin link 在当前上游存在已知行为风险，未通过隔离验证前不得进入 Production。

## Security, data and migration impact

预计数据库范围：

- `canonical_login_name(text)`、`login_name_claims` 与现有 Profile 的无冲突回填；
- `account_security_states`（无真实邮箱）；
- `registration_attempts`、`invitation_reservations` 与状态/index/constraints；
- server-only prepare/status/release、expected Auth UID/email binding、拒绝公开 Signup 的 PostgreSQL Before User Created Hook、Auth insert guard、expire/release/consume、verified activation、legacy redeem 的原子函数/trigger；
- 权限收紧：新函数默认 revoke `PUBLIC`、`anon`、`authenticated`，只对明确角色授权；所有 `SECURITY DEFINER` 固定空 `search_path` 并使用全限定名；
- 新 Audit action，不写 email、OTP、invite secret、password、token 或 Session credential。

预计应用范围：

- B1 最小 server-only registration broker；B2 接线、opaque attempt cookie 和 username sign-in broker；
- AuthProvider 的 signup verification、resend、recovery、password/email update 能力；
- 注册、验证码、重发、忘记密码、重置密码、账号安全和 legacy binding 页面；
- 中文 Auth/security email templates；
- 邮件/账号限流、Turnstile 和脱敏 observability。

## Rollout and rollback

1. B1 先在 local/QA 添加兼容 Schema，功能旗标默认关闭；现有登录注册行为保持不变。
2. B2 在 local/Preview 完成真实邮箱 signup/OTP、恢复和用户名登录代理，不接触 Production；必须先通过 direct-signup bypass、secret bundle 和防枚举测试。
3. B4a 先完成 Preview Custom SMTP、发送域 DNS、中文模板、bounce/complaint、额度和 migration-only sender 基础设施；这是 B3 的前置条件。
4. B3 才在与 Production Auth 版本/配置一致的隔离项目证明 legacy current/new arm、相同 UID、TOTP 和 Session 连续性；真实账号迁移仍需另行授权。
5. B4b 最后完成全链路 Preview Auth 回归并形成 Production 配置/回滚清单。Production SMTP、Email Confirmation 和任何真实迁移只在最终独立 Release Gate 中执行。
6. 任何阶段可以关闭新注册/绑定旗标并继续旧登录。已成功绑定的真实邮箱通常不回退；如 Auth identity 本身损坏，只能在获批事故流程中对同一 UID 恢复旧 alias、轮换 Session 并从备份核对 identity/factors。
7. Migration 必须可前向兼容；不得通过删除 Auth user、重建账号、回滚用户已确认写入或重挂 Role/Content 处理失败。

## Verification and review trigger

批准实施前必须完成：

- 本地与 Preview 证明 6 位 signup/recovery OTP、一次性、expiry、resend 和防枚举。
- 2 小时 reservation 的并发、超时释放、重复 verify、revocation、transaction rollback 和容量不超售 SQL 测试。
- PostgreSQL Before User Created Hook 对 direct public Signup 默认拒绝；Admin Create 不携带 proof metadata；Auth insert claim 必须对错误 UID/email、过期、撤销、并发/重放 fail closed，并随 AFTER INSERT 失败完整回滚。
- 同 UID email-change 前后 Profile、Membership、Role、Content、Identity、TOTP factor 和 Session inventory 对比。
- username broker 不向 browser、response、日志或普通 Data API 暴露 email/secret。
- `supabase db advisors`、RLS/grant contract、secret scan 和 Preview Auth logs 无 PII/credential 泄露。
- Custom SMTP 的 DKIM/SPF/DMARC、中文模板、bounce/complaint、额度和关闭 tracking 验收。

重新评审触发：更换 Auth provider、允许邮箱登录、支持同一邮箱多账号、引入 OAuth/passkey、改变 reservation 期限、改变 Admin MFA 或将邮箱复制到业务 Schema。

## Supersedes / superseded by

本 ADR 在 Proposed 阶段不改变 ADR-020。只有 Product Owner 将其标记为 Accepted 后，才 supersede ADR-020 中“不可投递邮箱、Email Confirm 关闭、无密码恢复通道”的决定；ADR-020 的历史背景和既有 Beta 证据永久保留。
