# ADR-022 — Admin Step-up Reauthentication Trust Boundary

- Status: Accepted — Option 3 / `ACCEPTED DEFERRED BOUNDARY`
- Date: 2026-08-17
- Decision owner: Product Owner
- Related: D-039, ADR-020, ADR-021, KI-033

## Decision

Product Owner 于 2026-08-17 选择 Option 3：当前 P1 延期全部 elevated mutations。

- 当前 P1 不建立自定义 server-only proof issuer，也不引入 Supabase MFA/AAL2。
- 当前 P1 只允许普通账户 Membership 治理与 Author Role Grant/Revoke；Admin/Super Admin Role Grant/Revoke 及任何 elevated-account Membership 变更均保持关闭。
- elevated 账户仍可按既定权限只读展示；所有写入控件必须不可执行，并明确说明需要未来 Reauth/MFA 阶段。
- 不得用普通 Session、Session 年龄、JWT `iat`、客户端 boolean、再次调用普通登录或其他弱化方案替代操作绑定 Reauth proof。
- 未来如重新启用 elevated mutations，必须获得独立 Product Owner 授权并建立新的 Auth ADR；届时优先评估 Supabase MFA/AAL2。

本决定把 KI-033 的当前 P1 状态更新为 `ACCEPTED DEFERRED BOUNDARY`，不代表技术问题已经解决，不降低 Reauth 要求，也不表示 elevated mutations 已验收。

## Context

P1-00 要求 Admin/Super Admin role grant/revoke，以及 elevated-account Membership 变更，在最终确认前重新验证当前 actor 的 registration name/password。proof 必须绑定当前 actor、当前 Admin Session、单次 Review payload 和一次消费；密码不能持久化或进入日志/Audit。

当前项目把 registration name 规范化后映射为不可投递的内部 email-shaped Auth identifier，再调用 Supabase `signInWithPassword()`。Admin 的正常 Session 由 `@supabase/ssr` cookie client 管理。

P1-01 必须判断这条适配层能否在不暴露密码、不使用浏览器 service role、不替换当前 Admin Session 的前提下形成数据库可验证 step-up。

## Official contract evidence

复核日期：2026-08-17。

- Supabase [`reauthenticate()` password security contract](https://supabase.com/docs/guides/auth/password-security) 用于安全密码变更，并向 confirmed email 或 phone 发送 nonce。本项目账号没有可投递 email/phone，因此它不是 registration-name/password step-up。
- [`signInWithPassword()`](https://supabase.com/docs/reference/javascript/auth-signinwithpassword) 验证 email/phone + password 并创建普通 Session；它不返回操作绑定 proof。
- [Auth server client](https://supabase.com/docs/reference/javascript/auth) 支持 `persistSession:false`、`autoRefreshToken:false`、`detectSessionInUrl:false`，可避免隔离登录写入浏览器 cookie，但不能证明哪个受控 server path 执行了密码验证。
- [User Sessions](https://supabase.com/docs/guides/auth/sessions) 说明 JWT `session_id` 对应 `auth.sessions`。Session 存在或新近创建只证明一次普通登录，不证明该 Session 专用于某个治理操作。
- [JWT claims](https://supabase.com/docs/guides/auth/jwt-fields) 与 [MFA](https://supabase.com/docs/guides/auth/auth-mfa) 将 password login 归为 `aal1`；`aal2` 需要附加 factor。
- [`signOut({ scope: "local" })`](https://supabase.com/docs/reference/javascript/auth-signout) 可撤销隔离 Session 的 refresh tokens，但其 access token 在到期前仍可能有效；因此 Token 必须只存在于受控 server memory 且绝不输出。

## Repository evidence

- `packages/auth/src/provider.ts` 只暴露 `getSession/signInWithPassword/signOut/signUpWithPassword`；没有 session ID、AAL、proof issuer 或 proof consumer。
- `createServerAuthProvider()` 与 Admin 当前 cookie adapter 会在登录时更新当前 cookie，不能直接用于不污染当前 Admin Session 的 step-up。
- `createPublicSupabaseClient()` 已展示无持久化 client 配置，但当前 Identity Access 路径没有隔离 Reauth adapter。
- `apps/admin` 只有 publishable key 配置；没有 server-only proof signing secret、narrow backend credential、Edge Function trust boundary 或数据库 proof registry。
- 当前三个 RPC 只看到调用 JWT 的 `auth.uid()`；任何持有普通 Session 的调用者都能直接调用，数据库无法区分“刚输入密码的受控 Server Action”和绕过 UI 的 RPC 请求。

## Feasibility proof result

技术结论：安全 registration-name/password step-up 仍未被证明可行。Product Owner 已通过延期全部 elevated mutations 接受这一当前 P1 边界；KI-033 不得标记为技术已解决。

现有 adapter 可以验证一组 registration-name/password 并获得相同 user ID，但以下安全属性无法同时证明：

1. 不替换当前 Admin cookie Session。
2. 数据库能验证密码检查确由受信 server boundary 完成。
3. proof 绑定原 Admin `session_id`，而不是任意新建 `aal1` Session。
4. proof 绑定 requestId、operation、target、expected-state、desired state 和 reason fingerprint。
5. proof 最多 5 分钟有效并且只能消费一次。
6. 浏览器不能伪造、复制或绕过 proof，直接调用 RPC。

仅在 Server Action 中先 `signInWithPassword()` 再返回 boolean 不合格：恶意或被借用的普通 Session 可以绕过 Server Action 直接调用 authenticated RPC。仅检查 JWT `iat`、Session creation time 或 `auth.sessions` row 也不合格：普通重新登录同样满足，且没有操作绑定。

因此 elevated mutation 的接口、proof schema、grant 和实现必须停止；不能以弱化验证完成 P1。

## Mandatory proof properties if elevated mutations are reconsidered

任何获准方案都必须：

- proof issuer 在 server-only trust boundary；浏览器无 signing/issuance credential。
- 密码只发送给 Supabase Auth password endpoint；不写数据库、日志、Audit、ledger、URL、客户端持久状态或错误。
- 使用隔离 client，禁止写当前 cookie；验证返回 user ID 与当前 actor 完全相同；隔离 Session 立即 local sign-out。
- proof 绑定 actor user ID、原 Admin session ID、requestId、operation、target user ID、expected-state token、desired state、normalized reason fingerprint。
- `issuedAt` 到 `expiresAt` 最大 5 分钟；数据库验证时钟、session 存在和 live actor role。
- proof ID 在 private schema 原子消费一次；同 requestId replay 先返回 ledger 原结果，不重新消费。
- 任一 Auth/issuer/consumer/cleanup 失败都零业务变化、零业务 Audit。

5 分钟只是未来重新设计时必须重新确认的最大有效期，不是当前已实现合同。

## Product Owner options

### Option A — Authorize a dedicated server-only proof issuer（not selected）

新增受信 server boundary：隔离 password sign-in 验证 actor 后，使用新的 server-only、可轮换、最小用途签名/issuance credential 生成操作绑定 proof；数据库 private consumer 验签并一次性消费。

要求：新增 secret lifecycle、issuer/consumer threat model、rate limit、Auth session cleanup、key rotation、incident response 和独立 Auth/Security Mission。不得使用浏览器 service role；不得给普通应用 Repository 一个通用 RLS-bypass client。

取舍：保持 registration-name/password UX，但明确扩大 Auth 架构和 secret 运维面。

### Option B — Replace password step-up with Supabase-native MFA/AAL2（not selected now; preferred future evaluation）

要求 elevated operator 注册 TOTP/受支持 factor，数据库检查当前 Session 的 `aal2` 和 session ID，并仍执行 operation-bound one-time intent。

取舍：官方 Auth 提供更强 factor 证明，但改变 P1-00 的 registration-name/password 决定，需要 MFA enrollment、recovery、lost-device、support 和 Auth 配置设计。

### Option C — Defer all elevated mutations（selected）

P1 只交付 read model 与获准的低风险 Author/普通 Membership 治理；Admin/Super Admin role 和 elevated-account Membership 保持关闭。本 ADR 不授权以人工流程、旧 RPC 或数据库直写替代这些关闭的产品能力。

取舍：安全边界最小，不扩大 Auth 架构；当前 P1 的 elevated governance 不交付，普通 Identity & Access Governance 可进入未来 P1-02 规划。

### Rejected — Treat ordinary password login/Session age as step-up

拒绝原因：没有操作绑定、一次性消费或可信 issuer；可被直接 RPC 绕过，不满足 P1-00。

### Rejected — Send password to database or persist it for replay

拒绝原因：扩大凭据暴露面，违反 Supabase password boundary 与 P1 安全合同。

### Rejected — Client self-attestation or long-lived flag

拒绝原因：客户端可伪造/重放，数据库不可验证。

## Consequences and reopening rule

- KI-033 当前 P1 状态为 `ACCEPTED DEFERRED BOUNDARY`；底层 Reauth feasibility 仍未证明。
- elevated mutations 状态为 `DEFERRED`；当前或未来普通治理实现不得包含其接口、grant、隐藏入口、旧 RPC 入口或客户端直写。
- 普通治理状态为 `AUTHORIZED FOR FUTURE P1-02 PLANNING`；这不是 P1-02 实施授权。
- 当前 P1 不创建 Reauth Migration、proof schema、secret、Edge Function、MFA 配置或远程测试。
- 最后一名 active Super Admin 的数据库保护必须保留，即使 elevated mutation surface 关闭。
- 重新开放 elevated mutations 必须通过独立 Product Owner 授权和新的 Auth ADR；不得仅修改本 ADR 状态或恢复旧 RPC execute。
- Admin Production 保持 `paused=true`。
