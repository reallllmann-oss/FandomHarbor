# ADR-017 — Vercel + Supabase 当前基线与传统云服务器迁移约束

- Date: 2026-06-29
- Status: Accepted
- Owners/reviewers: Product Owner / Tech Lead
- Related .ai decisions: D-008, D-009, D-011, D-029, D-031
- Related requirements/risks: KI-009, `docs/08_Security/RISK_ANALYSIS.md` R-13, `docs/14_Deploy/DEPLOYMENT_PLAN.md`

## Context

Fandom Harbor 当前选择 Vercel 承载 Next.js 应用，Supabase 提供 Auth、PostgreSQL 和 Storage。该方案适合当前团队规模和产品阶段，但成本、合规、数据驻留、容量、运行时限制或可用性要求可能使项目未来迁往传统云服务器。

如果现在为所有未来平台建设抽象和双套实现，会引入未被需求证明的复杂度；如果业务代码直接遍布 Vercel/Supabase 类型、生命周期和 URL，则未来迁移将变成高风险重写。因此需要在“不过度设计”和“不被平台渗透”之间建立可审计约束。

## Decision drivers

- 以最低运维复杂度完成当前产品验证。
- 保护私域内容、身份、RLS 与审计语义。
- 保持 PostgreSQL 数据、文件和配置的可导出、可恢复和可验证性。
- 使 Next.js 核心路径能在标准 Node.js 服务器上运行。
- 避免为未经证明的迁移预付双倍建设与测试成本。

## Options considered

### Option A — 充分使用平台专属能力，未来整体重写

初期实现最快，但 provider 类型、调度、文件 URL、缓存和身份语义会渗透业务层。迁移时难以分阶段验证和回滚。

### Option B — 现在建设 Vercel/Supabase 与自托管双实现

退出能力最强，但在没有规模、预算和目标云环境决策时会产生过度抽象、双倍运维和无法证明的兼容性成本。

### Option C — 当前平台单实现 + 可执行边界 + 分阶段退出路径

使用 Vercel + Supabase 交付当前系统，只在身份、数据库、文件、后台任务、运行时配置和可观测性建立窄边界。有证据需要迁移时，先迁计算层，再独立处理 Storage、PostgreSQL 和 Auth。

## Decision

选择 Option C。

1. 当前生产基线为 Vercel + Supabase。本 ADR 不授权创建传统云服务器、容器、队列、新数据库或新 Auth 实现。
2. 业务与领域代码只依赖项目内部合同；Vercel/Supabase SDK 类型、response、URL 和错误对象不得成为公开领域合同。
3. 平台依赖收口到现有 `packages/config`、`packages/auth`、`packages/database` 和 `packages/services`。接口只覆盖已批准用例，不伪造一个能镜像所有 provider API 的通用平台。
4. 核心服务端路径使用标准 Node.js 24.x，应用进程无状态且不依赖本地持久磁盘、单实例内存锁或 HTTP 请求存活执行长任务。
5. PostgreSQL migration、RLS、grant、function、extension 与 Storage policy 必须在仓库可审查、可重建；平台 Dashboard 不是唯一事实源。
6. 迁移只在成本、合规、容量、可用性或平台限制有证据时启动。默认顺序是：计算层→Storage→PostgreSQL→Auth/其他平台能力。Auth 可以永久保留在 Supabase，不是必然迁移项。
7. 每个执行阶段需要新 ADR 或批准的执行计划，包括等价性测试、安全审查、导出/恢复演练、可观测性、流量切换、观察窗口和回滚点。

## Consequences

### Positive

- 保留 Vercel + Supabase 的当前交付效率，不引入无证据的双基础设施成本。
- 平台渗透被限制在可审计模块，可以通过替换 adapter 而不是重写领域流程迁移。
- 计算、文件、数据库与身份可独立验证和回滚，降低一次性切换风险。
- 仓库 migration 与恢复演练同时改善当前灾备能力，不只服务于未来迁移。

### Negative / trade-offs

- 每个 provider 调用都需要明确的边界与合同测试，初期代码量高于在页面或业务服务中直接调用 SDK。
- Supabase Auth/Storage 包含平台管理 schema 和语义，接口边界只能降低、不能消除实际数据迁移成本。
- 为保持可迁移性，某些 Edge-only 优化只能作为可选快速路径，不能成为唯一实现。
- 分阶段迁移期间可能临时存在跨公网访问延迟与出口成本，需要容量测试决定是否接受。

## Security, data and migration impact

- 计算层迁移不改变服务端授权 + PostgreSQL RLS 的双层强制；所有 allow/deny 矩阵必须在目标环境重新通过。
- 密钥必须在目标密钥管理中重新注入并轮换，不通过镜像、日志、导出物或配置文件迁移。
- 私有文件迁移必须校验 checksum、metadata、授权、retention 与 deletion semantics，并保持稳定业务 file ID。
- PostgreSQL 迁移必须校验数据完整性、RLS/grant/function/extension 等价性、审计链路和回滚后写入处理。
- Auth 迁移必须独立评审身份映射、credential、session、MFA、recovery、email 和 revoke semantics；不得由数据库迁移隐式授权。

## Verification and review trigger

在代码阶段通过以下证据持续验证本 ADR：

- 架构/依赖检查证明 Vercel/Supabase SDK 只出现在批准的 adapter 边界。
- 标准 Node.js 环境中的 build、server startup、health/readiness 与核心请求测试通过。
- 从仓库重建 PostgreSQL schema、RLS、grant 和必要 policy 后，允许/拒绝测试结果一致。
- 备份与导出物在隔离环境恢复后，数据、文件、权限与审计完整。

当成本、合规、容量、可用性、平台限制或事故证明需要实际迁移，或者引入了新的 Edge-only、database、storage、auth、queue 或 orchestration 依赖时，必须复审本 ADR。

## Supersedes / superseded by

本 ADR 不替代 ADR-001 或 ADR-007，而是为其增加部署与退出约束。未来的实际迁移 ADR 必须引用本记录，并明确哪些约束被保留、替代或废弃。
