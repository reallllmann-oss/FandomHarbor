# ADR-020 — 注册名凭据与邀请码原子注册

- Date: 2026-07-02
- Status: Accepted
- Owners/reviewers: Product Owner / Tech Lead
- Related .ai decisions: D-003, D-005, D-011, D-033, D-037; DD-007
- Supersedes: ADR-018 的用户邮箱、强制邮箱验证和 Auth SMTP 部分

## Context

Phase 2 人工验收发现邮箱验证不符合产品规则，并使注册受到验证邮件速率限制。产品要求用户只提供注册名、密码和邀请码，同时无效邀请码不得留下 Auth 用户、Profile 或 Membership。

Supabase 密码认证仍需要内部 email-shaped identifier，但这不需要成为用户凭据。现有 Membership、Invitation、`role_grants` 与 RLS 权限模型必须保持不变。

## Decision

- 注册输入固定为注册名、至少 8 位密码和邀请码；登录输入固定为注册名和密码。
- 注册名规范化后派生不可投递的内部 Supabase Auth 标识，用户界面和业务合同不暴露该标识。
- `profiles.registration_name` 保存站内注册名，并通过 `lower(registration_name)` 唯一索引实现大小写不敏感唯一。
- Server Action 对邀请码明文计算 SHA-256；数据库和 Auth metadata 只接收 hash。
- 匿名预检函数只返回邀请码当前是否可用；最终权限判断仍由注册触发器在锁定邀请行后执行。
- `auth.users` 的 password signup 插入触发器在同一事务创建 Profile、active Membership、Invitation Redemption、邀请码计数与审计记录。任何失败都会回滚 Auth 用户插入。
- Email Confirm 必须关闭，不发送注册验证邮件。密码不要求大小写、数字或特殊字符。
- Trusted Identity 只保存 Auth user ID。注册 metadata 不作为会话身份、Membership 或角色授权事实源。

## Consequences

### Positive

- 注册流程不依赖收信或 SMTP，不受邮件发送频率限制。
- 无效邀请码和重复注册名不会留下半成功账号。
- 注册名与权限事实分离；现有 active Membership 和手工高权限角色模型保持不变。

### Trade-offs

- Supabase Auth 内部仍保存不可投递的 email-shaped identifier，这是 provider 适配细节。
- 密码找回尚无用户邮箱通道，必须在后续独立产品/安全 Sprint 决策，不能假装已有找回能力。
- 目标 Supabase Project 必须显式关闭 Email Confirm；仓库内 `supabase/config.toml` 已固定本地行为，但远程配置仍需部署验收核对。

## Security and verification

- SQL 测试覆盖有效邀请码、未知邀请码、大小写重复注册名、零残留回滚、Membership、Redemption、邀请码计数和无高权限授予。
- 真实本地 Auth API 验证 signup 与 password login 均直接返回 Session，且没有邮件步骤。
- 邀请 hash、Membership 与角色仍不接受 URL/client owner 参数作为授权事实。

## Review trigger

引入密码找回、邮箱绑定、OAuth/Magic Link/MFA、修改注册名、公开注册、改变邀请码资格或替换 Supabase Auth 时必须复审。
