# ADR-024 — TOTP/AAL2-Bound Super Admin Commissioning

- Status: Accepted — architecture boundary; implementation blocked pending feasibility proof
- Date: 2026-09-19
- Decision owner: Product Owner
- Related: D-040, ADR-021, ADR-022, ADR-023, KI-033, Admin P1-07C

## Decision

Product Owner 选择 ADR-022 的 Option B：Supabase TOTP/AAL2 加一次性、操作绑定 intent。此次重新开放只授权设计一个 elevated operation：

- operation：`grant_super_admin`；
- actor：当前 live、authenticated、active 的 Super Admin，初始唯一授权操作者为 `Phase2RemoteInviter`；
- target：初始唯一授权目标 `akumie`；
- purpose：在最终 ordinary-write Cutover（Migration D）前建立第二条由 Product Owner 独立控制、可实际使用的 Production Super Admin 路径。

`aal2`、已注册 MFA、JWT `iat`、Session 年龄、客户端 boolean 或重新普通密码登录都不能单独授权该操作。最终确认必须同时验证 fresh TOTP `amr`、原 Session、冻结 payload、live Super Admin 权限、目标状态、一次性消费与原子 Audit/结果记录。

本 ADR 不授权实现、QA、Production MFA enrollment、Role 写入、Migration、部署或 Admin Resume。Session 保持、AMR 刷新语义和 Migration D 兼容性仍须 P1-07C-4A5 在非 Production 证明。

## Historical boundary

[ADR-022](ADR-022.md) Option C 对冻结的 ordinary-governance P1 范围仍是正确的历史决定。它阻止了在没有合格 step-up proof 时开放 Admin/Super Admin Role 或 elevated-account Membership 写入。

本 ADR 不改写 ADR-022，也不把 KI-033 追溯标记为已解决。它是在 Product Owner 独立授权下，为 `grant_super_admin` 单一 commissioning 目的建立的新边界。除该操作外，ADR-022 的延期状态继续生效。

## Explicitly not authorized

- Grant/Revoke Admin；
- Revoke Super Admin；
- elevated-account Membership mutation；
- generic role mutation 或 arbitrary target UI；
- 通过旧 RPC、数据库直写、service-role browser client 或人工 SQL 绕过；
- 完整 P1.1 Elevated Access Governance；
- P1-08 runtime navigation；
- Migration D、Production deployment、Admin Resume 或 Web Admin Entry 开放。

## Official Supabase contract reviewed

复核日期：2026-09-19。先检查当前 [Supabase Changelog](https://supabase.com/changelog)，未发现改变本决定所依赖的 hosted MFA 合同的条目。

- [MFA](https://supabase.com/docs/guides/auth/auth-mfa) 将普通 password session 归为 `aal1`，成功附加 factor 后 JWT `aal` 为 `aal2`；应用仍须在数据库/API 强制执行。
- [TOTP MFA](https://supabase.com/docs/guides/auth/auth-mfa/totp) 使用 enroll、challenge 和 verify。verified factor 与成功 challenge 才能形成 TOTP 证明。
- 官方 MFA 文档说明 JWT `amr` 是按最新方法优先排序的 `{ method, timestamp }` 数组；`amr[0]` 是最新认证方法。最终确认必须要求最新相关 entry 的 `method = totp`。
- [JWT Claims](https://supabase.com/docs/guides/auth/jwt-fields) 定义 `aal`、`amr` 和 `session_id`。数据库只信任由 Supabase 签发并通过当前请求带入的 claims，不信任客户端复制值。
- [User Sessions](https://supabase.com/docs/guides/auth/sessions) 说明 `session_id` 对应 `auth.sessions.id`；Single Session 策略在 refresh 时执行。项目的实际 Session 策略与 MFA verify 后的 Session ID 行为仍须专门 proof。
- 官方 enroll reference 说明完成 factor verification 会把当前 Session 提升为 `aal2` 并登出其他 Session。它没有在本项目适配层下证明 `session_id` 必然保持，因此本 ADR 不作该假设。
- 当前官方恢复建议是注册独立 backup TOTP factor；factor unenroll 后 AAL downgrade 可能要到 refresh 或显式 `refreshSession()` 才生效。因此每次 privileged confirm 都必须重新读取 live Session/factor 状态，而不能依赖旧页面。

本项目当前 `AuthProvider` 只返回 identity 与 expiry，不暴露 `session_id`、`aal` 或 `amr`；`createServerAuthProvider()` 依赖 SSR cookie adapter。`supabase/config.toml` 的本地 TOTP enroll/verify 当前为 disabled。这些都是实现工作和 feasibility proof 的明确缺口。

## Proof and freshness contract

最终 `grant_super_admin` confirmation 必须同时满足：

1. `auth.uid()` 等于 intent 的 `actor_user_id`；
2. JWT `session_id` 等于 intent 的 `actor_session_id`，且对应 live `auth.sessions` row；
3. actor Membership 仍为 active，且仍有未撤销 `super_admin` grant；
4. JWT `aal = aal2`；
5. 最新相关 `amr` entry 为 `method = totp`；
6. TOTP AMR timestamp 晚于 intent 创建时冻结的 prior TOTP AMR timestamp，证明本 intent 后发生了新 challenge/verify；
7. AMR timestamp 不早于 intent 的 challenge-not-before boundary，且从 AMR 到数据库确认不超过 5 分钟；
8. intent 未过期、未消费，且当前数据库时间不晚于 `expires_at`；
9. requestId、operation、target、desired role、expected-state token 与 normalized reason fingerprint 全部相同；
10. target 仍满足 exact commissioning policy 与 expected state；
11. 同一 Session/TOTP AMR evidence 未被另一 intent 消费；
12. mutation、业务 Audit、ledger 结果和 intent consume 在同一事务提交。

5 分钟是最大窗口，不是“Session 在 5 分钟内即可”的替代规则。A5 必须证明 `amr` 的时间精度与再次 challenge/verify 的刷新行为；如果无法可靠区分 intent 前后的 TOTP 事件，方案保持 fail closed。

## Enrollment and operational gate

三个问题的决定均为 **YES**：

1. `Phase2RemoteInviter` 必须在 grant 前完成 TOTP enrollment、verification 和 fresh AAL2 proof。
2. `akumie` 必须在收到 Super Admin 前完成自己的 TOTP enrollment/verification；普通账号可在不获得 Admin capability 的独立 account-security flow 中完成此步骤。
3. `akumie` 只有在以自己的 Session 完成 TOTP、得到 AAL2 并通过只读 Admin authorization smoke 后，才计入“可操作冗余 Super Admin”。

每个 operational Super Admin 至少登记两个分别保管的 verified TOTP factors：primary 与 backup。Enrollment QR、secret 和 TOTP code 只能短暂显示/提交，不进入日志、Audit、ledger、URL、测试夹具、截图或文档。

Enrollment 与 commissioning 分离：先完成 factor enrollment，再开始 elevated Review。Enrollment 可能登出其他 Session；因此不得在 enrollment 前创建将被随后 Session 变化破坏的 intent。

## Private operation-bound intent

未来 Migration 在非 Data API 的 private schema 建立 intent state。应用角色不得直接 SELECT/INSERT/UPDATE/DELETE。最小字段：

- `intent_id`；
- `request_id`；
- `actor_user_id`；
- `actor_session_id`；
- `operation`，初始约束只允许 `grant_super_admin`；
- `target_user_id`；
- `expected_state_token`；
- `desired_role`，固定为 `super_admin`；
- `normalized_reason_fingerprint`；
- `prior_totp_amr_timestamp` 与 challenge-not-before boundary；
- `created_at`、`expires_at`、`consumed_at`；
- consumed MFA evidence key；
- result/ledger/Audit reference。

Intent 由数据库受控入口从 live actor、private commissioning policy 和 server-validated Review 创建。浏览器只持有 opaque intent ID；不能提交 trusted boolean、actor ID、operation、desired role 或任意 target 来改变决定。

Intent 的 maximum lifetime 为 5 分钟。失败的 MFA、Session 不匹配、过期或 payload drift 不产生业务 Audit 或 Role 变化。Conflict/成功等终态消费 intent；需要重试 MFA 的可恢复失败是否增加 attempt counter、何时强制作废，须在 A5 threat test 冻结。

## Exact lifecycle

1. live Super Admin 打开 exact target Review；
2. 服务端重新读取 target，并冻结 requestId、expected-state、reason、operation 与 desired role；
3. 数据库从 private policy 选择 exact actor/target，建立 intent，并记录创建时的 prior TOTP AMR；
4. actor 在同一 current Session 完成 TOTP challenge + verify；
5. SSR cookie adapter 接收 Supabase 返回的新 token；
6. confirmation RPC 在任何业务写入前执行全部 proof、live authorization、target、requestId 和 replay 检查；
7. 取得 request/global-governance/Super-Admin advisory locks，重新计算 expected state；
8. 同一事务消费 intent、插入 Super Admin grant、写一条业务 Audit、写 ledger result；
9. 结果集合继续冻结为 `Saved | Unchanged | Conflict`：首次成功 grant 返回 `Saved`；目标 already granted 且 expected-state 匹配时返回 `Unchanged`；同 requestId/same payload replay 返回 ledger 原结果；
10. 不同 payload 同 requestId 返回 `REQUEST_ID_MISMATCH`；state drift 返回 `Conflict` 并零业务 Audit。

任一检查或事务组件失败：零 Role 变化、零业务 Audit、零 result ledger，并且不得出现与业务结果不一致的部分 intent consume。

## RequestId global uniqueness

复用现有 `private.identity_access_request_ledger` 作为结果权威，并把其 operation allow-list 扩展为 `grant_super_admin`。不建立第二个结果 ledger。

Intent 的 `request_id` 唯一。ordinary executor 和 elevated intent/confirm 必须使用同一个 request advisory-lock namespace，并在锁内同时检查 ledger 与 intent。这样一个 requestId 无法先后或并发代表 ordinary 与 elevated 两个 payload。过期/失败 intent 的 requestId 仍保留 tombstone；不得因 cleanup 重新释放命名空间。

同 requestId、同 elevated payload 在已有 ledger result 时返回原结果；同 requestId、不同 payload 或 actor 一律 fail closed。

## Exact target policy

Initial implementation 不接受可变 actor、operation、role 或 target：

- private commissioning policy 在 server/database boundary 解析并保存 `Phase2RemoteInviter` 与 `akumie` 的稳定 user IDs；
- public begin/confirm signatures 不提供可任意替换 target 的信任参数；
- Migration apply 时必须断言两者各自恰有一个 valid Auth user/identity、active Membership，actor 是 live Super Admin，target 尚无 Admin/Super Admin active grant；
- confirm 时重复全部断言，且 target 不能等于 actor；
- client bundle 不包含 credentials、factor IDs 或 private user IDs；
- `Reader11` 不在 policy 中且必须保持不变。

Target 任一漂移均返回安全 Conflict/Forbidden，零 Role/Audit 变化。

## Legacy elevated bypass closure

### Selected — Pattern 1: Pre-D compatibility migration

在新 elevated path 对应用角色可执行的同一原子 Migration 中：

- 保留 legacy `grant_role` 的 Author ordinary 行为；Admin/Super Admin 分支 fail closed；
- legacy `revoke_role` 的 Admin/Super Admin 分支 fail closed；Author ordinary 行为保留；
- legacy `set_membership_state` 对任何当前 elevated target fail closed，普通 target 行为保留；
- 安装 private intent/proof consumer 和 exact `grant_super_admin` RPC；
- 新 RPC 只向 `authenticated` 授准确签名 execute，所有 private helper 继续对应用角色 deny；
- 不增加同名 overload，不改变三个 legacy 函数的 signature、`VOLATILE SECURITY DEFINER`、owner `postgres` 或空 `search_path`。

这使旧 elevated 路径与新合规路径在一个事务边界完成“关闭/打开”，不存在可利用的中间 bypass。

### Rejected — Pattern 2: make legacy signature consume proof

现有 legacy signatures 没有 requestId、intent、expected-state 或 Session binding；用隐式客户端状态包装会恢复 UI-only trust。新增同名 overload 还会使 Migration D 的六函数 catalog count 失败。

### Rejected as primary — Pattern 3: revoke all legacy writes early

完全撤销 legacy execute 可以关闭 bypass，但会在 D 前中断仍需保留的 ordinary legacy 行为。它只可作为 incident fail-closed fallback，不是正常 commissioning 路径。

### Rollback

Rollback 只能向更封闭状态前进：撤销新 elevated RPC execute、冻结所有未消费 intents，并保持 legacy elevated 分支拒绝。不得重新开放旧 elevated RPC。若 ordinary UI 回滚，legacy ordinary behavior 可保留到 D；D 完成后旧 RPC 仍不得恢复。

## Migration ordering and D compatibility

当前 Production 已应用至 C：`20260817125140_admin_p1_identity_access_writes.sql`；D 为 `20260819225318_admin_p1_identity_access_cutover.sql`，尚未应用。

未来 Auth/intent/compatibility Migration 必须使用唯一 version，排序严格位于 C 与 D 之间。原因：Supabase CLI 按 timestamp 对 local/remote history 比对并按顺序应用；晚于 D 的文件不能在不制造 history drift 的情况下先于 D 执行。

预期序列：

1. Production 19/21：A/B/C 已应用；新 Pre-D 与 D pending；
2. 隔离 frozen workspace 只暴露 through Pre-D，`supabase migration up --linked` 唯一 pending 为 Pre-D；
3. Production 20/21：Pre-D applied；D 仍 pending；
4. 完成 MFA enrollment、compliant grant、`akumie` operational smoke、fresh backup 和 P1-07C-4A rerun；
5. 独立授权执行原 D；Production 21/21。

D 本身无需按当前静态分析修改：它只要求六个既有函数各有唯一准确 signature，验证其 owner/security/volatility/search path，要求 v2 仍 execute-closed，然后 revoke legacy 并 grant v2。Pattern 1 保持这些 catalog 属性且新增 RPC 使用不同名称。

但这只是 architecture compatibility。A5/implementation 必须用 future Migration 文件完成：exact `pg_get_functiondef`/catalog precondition、clean rebuild、C→Pre-D→D upgrade、Hosted ACL、private deny、rollback、并发与最终 D replay proof。证明前，本项状态为 **REQUIRES PROOF**；不得执行 D。

## Audit and result contract

成功必须精确产生：一个 Super Admin grant、一个业务 Audit、一个 request ledger result、一个 consumed intent。Audit 使用既有角色治理语义并包含非秘密字段：

- actor、operation、target、desired role；
- normalized reason；
- requestId；
- opaque intent/proof reference；
- expected-state reference；
- result 与 role grant reference；
- non-secret TOTP method/timestamp evidence reference。

不得记录 TOTP code、factor secret、password、access/refresh token、Cookie、完整 JWT、service key 或 database credential。Failed MFA 不写 role-grant business Audit；可选安全 telemetry 只能记录安全错误分类和 opaque intent reference，且不得泄漏 target existence 或凭据。

## Recovery and lost-factor boundary

- 每个 operational Super Admin 在独立设备/保管位置维护 primary 与 backup verified TOTP factor；不得共享 seed。
- primary 丢失时使用 backup factor登录，重新 enroll 新 backup，并 revoke 丢失 factor；随后 refresh/重新认证，旧 AAL2 token 不得继续作为 proof。
- 初始产品不向 active Super Admin 提供可使 verified factor 数低于恢复下限的普通自助 removal flow；即使用户通过 provider API移除，后续 live factor check 必须立即使 elevated confirm fail closed。
- 全部 factors 丢失时不得用 password-only、旧 RPC、数据库 role 直写或延长 Session 绕过。由 Product Owner 单独授权 platform-level break-glass，验证账号控制、吊销 Sessions、删除失效 factor、重新 enroll，并记录独立安全证据。
- 当前另一名受控 Super Admin 是恢复期间的业务连续性路径；如果两人同时失去 factors，Admin 保持 paused/elevated mutation closed，等待平台级恢复。
- Supabase 当前推荐 backup TOTP factor；任何 future recovery-code 能力必须单独确认正式支持、存储和轮换合同，不能替代本 ADR 已冻结的 backup-factor policy。

## Two-Super-Admin gate

数据库 active Super Admin count = 2 不是完成条件。Gate 必须同时证明：

- 两个账号为 Product Owner 独立控制的真实 Production identities；
- valid Auth user/identity 与 active Membership；
- active Super Admin grant；
- 各自符合 factor/recovery policy；
- 各自能以自己的 Session 完成 TOTP/AAL2；
- `akumie` 独立完成只读 Admin access smoke；
- 没有账号共享、QA identity 或 test credential。

## Feasibility proof required before implementation

P1-07C-4A5 必须在 dedicated non-Production Supabase 证明：

- Production-equivalent TOTP settings；
- enrollment、second factor、challenge/verify 与 removal/downgrade；
- challenge/verify 后 `session_id` 是否稳定，原 Admin Session 是否继续可用；
- SSR cookie adapter 能否安全接收新 token 且不丢失 DB-backed Review intent；
- fresh `amr[0] = totp`、timestamp 更新、5-minute boundary 与 replay rejection；
- Single Session setting/refresh 不会意外终止原 actor Session；
- intent/ledger global requestId、atomic rollback、concurrency 与 payload mismatch；
- legacy bypass closure和 C→Pre-D→D upgrade compatibility。

任何核心性质未证明，状态都保持 `FEASIBILITY REQUIRED`，不得弱化为 AAL2-only。

## Release impact

`b494b5e954ce0d43e28df088bd3f2c0c7a19b31f` 继续作为历史 P1 frozen release baseline，但引入新 Auth/DB/runtime 合同后不能作为最终 candidate。

未来顺序：ADR accepted → A5 feasibility proof → implementation branch → local tests → dedicated QA → protected Preview → new release SHA → Production preflight → controlled Auth/Pre-D Migration → `Phase2RemoteInviter` enrollment → compliant grant `akumie` → `akumie` TOTP/AAL2/read-only smoke → two-SA gate → fresh current-state Pre-Cutover Backup → rerun P1-07C-4A → final D → post-cutover validation。

2026-09-16 backup 是有效历史证据，但其后已有 `akumie` password reset/login 及 Production A/B/C Migration，因此不是 final current-state Pre-Cutover Backup。

## Future P1-08 product requirement — Unified Account Navigation

记录为未来已授权产品需求，但本 ADR 不实现：

- 一个账号可以同时拥有阅读、Author Studio、Admin/Super Admin capabilities；
- Web 只在 live Admin/Super Admin 时显示“管理后台”，未授权用户不显示；Admin 仍独立实时授权；
- Author capability 正常显示 Author Studio，同账号可同时显示多个入口；
- Admin 全局导航提供“返回主站”，无需 logout；
- 旧缓存链接不能绕过 live revocation；
- Web Admin Entry 当前继续 CLOSED，只有 Admin Production、session/domain 行为与 Product Owner 独立授权全部通过后才能开放。

## Consequences

### Positive

- 使用 Supabase 原生 TOTP/AAL2 作为 factor evidence，同时由数据库 intent 补齐操作绑定、时效与一次消费。
- exact actor/target/operation 将当前紧急 commissioning 需求与未来通用 elevated governance 隔离。
- Pattern 1 在不提前执行 D 的前提下关闭旧 elevated bypass，并保留 ordinary continuity。
- requestId、Audit、ledger 与 existing expected-state 语义保持一个权威体系。

### Negative / trade-offs

- 需要 Auth adapter、UI、数据库和运维恢复合同的新实现与专门 QA；frozen runtime candidate 必须更新。
- TOTP enrollment 会影响其他 Session；当前 Session ID/SSR cookie 行为尚未在本项目证明。
- 在 Pre-D Migration、两个账号 enrollment、compliant grant、新备份和 re-audit 完成前，Migration D 继续 blocked。

## Review triggers

以下任一变化必须新 ADR 或 Product Owner 独立授权：新增 elevated operation/target、改变 5-minute window、使用非 TOTP factor、引入 recovery codes、改变 factor minimum、允许 target self-selection、改变 legacy closure pattern、修改 D、开放 Web Admin Entry、恢复 Admin Production 或开展完整 P1.1。
